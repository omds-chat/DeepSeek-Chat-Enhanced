# 信任与签名：网页产物与插件产物

> 本文负责：把网页产物与插件产物的签名链路、三态结论、失败处理口径，以及作者签名的覆盖边界讲清楚，供实现与评审对照。本文不负责：证书如何签发与轮换、公私钥如何保管、分发结构如何组织、三层清单的字段格式与验签命令，这些见 [信任链与 PKI 签名](../user/develop/basic/trust-chain.md) 与 [网页签名与运行时校验](../user/develop/basic/web-signature.md)；安装记录如何存储见 [插件安装与存储](plugin-install-and-storage.md)；清单字段与能力语义见模板仓库的 [运行时规范](https://github.com/omds-chat/dsc-plugin-template/blob/main/specs/plugin-runtime-spec.md) 与 [开发规范](https://github.com/omds-chat/dsc-plugin-template/blob/main/specs/plugin-develop-spec.md)。

## 一、两条链路共用一个信任锚

网页产物与插件产物是两条独立的签名链路，但它们认同一个锚：构建时内嵌进产物的根证书。在线副本只用于比对与便利，不参与任何决策；根证书不能用自己验证自己，因此“在线拿到的根证书与内嵌不一致”只能提示，不能换锚。

链路分四段：前两段是串联的，顺序不可交换；后两段各自独立，不通过不影响前两段。

| 段 | 验什么 | 通过后才有资格进入下一段 |
|:---:|:---:|:---:|
| 根 CA → EEC | 终端签名证书是否由内嵌根证书签发、是否在有效期内、是否被吊销 | 是，链不通过不做 CMS 验签 |
| EEC → 文件 | 分离签名是否由该 EEC 对文件原始字节生成 | 是 |
| 目录数据 | 三层哈希清单是否覆盖了目录文件，清单签名是否有效 | 否，属于独立结论，失败只降级 |
| 作者 → 产物 | 作者裸签名是否由作者公钥对同一份字节生成 | 否，属于另一条信任路径 |

“链不通过不做 CMS 验签”是这条链路最重要的一个取舍：证书链回答“签名者有没有资格”，CMS 回答“这份字节是不是它签的”。资格不成立时继续验签只会得到一个无法解释的布尔值，还会掩盖真正的原因。

## 二、网页产物的链路

### 2.1 根 CA 与网页 EEC

网页 EEC 是给网页产物签名的那张终端证书。它在在线时优先取分发副本，但必须先在内嵌根证书下通过链校验；取不到、无法解析或链不通过，一律回退到构建内嵌的那一份。离线时不发任何材料请求，直接用内嵌材料。

回退不是“降低标准”，而是承认两种材料在判据上不等价：在线副本是待验证的输入，内嵌材料是构建产物的一部分，前者不能替代后者。

### 2.2 清单与逐文件 CMS

网页签名不是“签一个哈希列表”，而是“清单签名 + 每个文件各签一份”：

| 对象 | 签名文件 | 作用 |
|:---:|:---:|:---:|
| 页面入口、主包与异步分包、样式 | 每个文件一份 `.sig` | 证明该文件的字节与签名时一致 |
| 清单 `web_files.json` | `web_files.json.sig` | 证明“应当校验哪些文件”这份列表本身没被改 |

校验顺序是先清单、后逐文件：先验清单签名，再按清单逐文件验签，并发有上限，失败会汇总成一条提示。清单里只允许相对路径，不允许绝对路径、上跳路径与带协议的地址——否则清单可以把自己指向站外。

这套结构解决的问题是“部分替换”：单独替换一个文件会失败，替换清单再替换文件也会失败，因为清单签名对不上。

### 2.3 运行时表现

页面挂载后异步校验一次，不阻塞渲染，且只执行一次。根证书未注入、环境没有 WebCrypto、产物没有清单，三种情况都静默返回；链或清单失败提示一条，逐文件失败汇总提示一条。没有重试，没有弹窗，页面照常运行。

网页签名不落盘，不改变任何界面状态：它是一次性的自检，结论只存在于当次提示里。

## 三、插件产物的链路

### 3.1 合集 CMS 对 plugin.js

插件产物的合集签名是 `plugin.js.sig`，逐字节语义，签名者是该来源的 EEC。引擎拿到证书后先在本机校链，链通过才做 CMS 验签；链不通过直接给失败结论，日志里留一条“链未通过、CMS 已跳过”的记录。

证书的取用顺序固定为：调用方已给的那份（信任清单登记或安装记录里已存的）、来源站点的规范路径、来源站点的旧兜底路径。前一项取到就不再请求后一项；两条来源路径都取不到，按“拿不到证书”处理。

### 3.2 三层清单只覆盖目录数据

合集把目录数据分成三层，每层一份哈希清单与一份清单签名，层与层互不引用。清单覆盖的是 `meta.json`、`plugins.json`、作者公钥、版本列表这类目录文件，不覆盖 `plugin.js`。产物由 `plugin.js.sig` 单独负责。

这条分工决定了两件事：目录数据被改不会让产物验签失败，产物被改也不会让目录清单失配；两者是独立结论，不能互相顶替。目录数据校验失败的后果是“目录数据未校验”，而不是“插件不可信”。

### 3.3 作者签名

作者签名是 Ed25519 裸签名，直接对 `plugin.js` 的原始字节签名，不做摘要预处理，也不需要证书。作者公钥随合集分发，验签前先用二层清单登记的哈希把关：公钥字节与哈希不一致时不采用该公钥，作者签名按未校验处理。

作者签名与合集签名是两条独立路径，互不替代。两种材料都有时必须同时通过才算通过；只有一种时只校验该种；都没有时为未校验。

## 四、三态结论

一次验签的结论只有三态。插件侧落盘、展示与判定都用这三个状态；网页侧不落盘，只用于当次提示：

| 状态 | 含义 | 触发条件 |
|:---:|:---:|:---:|
| 通过 | 有材料，且校验通过 | 合集材料或作者材料至少一项存在并全部通过 |
| 未校验 | 没有可校验的材料 | 两种签名材料都不完整 |
| 失败 | 有材料，但校验未通过 | 链不通过、CMS 不通过、作者签名不通过，任一成立 |

三态是“单元结论”，回答的是“这份字节与签名时是否一致”。它与来源结论是两条不同的轴：

| 维度 | 取值 | 回答的问题 | 是否落盘 |
|:---:|:---:|:---:|:---:|
| 签名状态 | 通过、未校验、失败 | 字节与签名是否一致 | 是 |
| 来源结论 | 已确认、未通过、无法确认、本地 | 签名者是否被本机信任 | 是 |

两条轴可以组合出看似矛盾、实则正常的状态：

| 组合 | 为什么会出现 |
|:---:|:---:|
| 通过 + 未通过 | 作者签名通过，但没有合集证书，来源无法确认 |
| 未校验 + 无法确认 | 调用方没有给任何来源材料 |
| 通过 + 已确认 | 链通过且 CMS 通过 |
| 失败 + 未通过 | 链不通过或验签不通过 |

三态不表达“部分通过”。合集签名与作者签名都有材料时，任一不通过整体即为失败；明细只在日志与界面原因里体现，不进入落盘状态。

## 五、失败只警告、不阻断

这条口径贯穿网页与插件两侧，但两侧的表现形式不同。

| 环节 | 行为 | 记录 | 用户可见 |
|:---:|:---:|:---:|:---:|
| 网页证书链或清单失败 | 不继续逐文件校验，页面照常运行 | 无落盘 | 一条警告 |
| 网页逐文件失败 | 汇总失败数量与前几个文件名 | 无落盘 | 一条警告 |
| 安装时验签失败 | 仍然安装并激活 | 签名状态记为失败 | 一条警告 |
| 恢复时验签失败 | 仍然加载并激活 | 签名状态失败，记录标记为不可信 | 一条警告 |
| 合集证书被吊销 | 仍然安装 | 吊销结论随来源材料传入时，记录标为不可信 | 一条警告 |
| 来源证书缺失 | 仍然安装 | 来源结论为未通过，原因单列 | 提示“来源证书缺失” |
| 产物字节取不到 | 拒绝安装 | 不标记不可信 | 安装拒绝原因“产物取不到” |
| 吊销列表不可用 | 吊销状态按未知处理 | 不据此判定证书被吊销 | 无额外提示 |
| 在线根证书与内嵌不一致 | 仍按内嵌根证书校验 | 无落盘 | 一次提示 |

三个理由支撑这条口径：

- 浏览器里已经加载的脚本无法被“撤回”，阻断只会制造“页面坏了”的观感，不会恢复安全状态。
- 阻断会把用户推向不受管的分发方式（例如自行打包离线包），结果是既失去警示也失去记录。
- “可见的不可信记录”比“静默拒绝”更有用：用户可以据此决定是否继续使用，也能在事后追溯。

边界同样明确：字节取不到时按网络问题拒绝安装，因为分不清网络失败与拦截篡改，此时给“不可信”结论会误伤；本地离线包没有来源，不参与来源判定，只给作者签名结论。

## 六、作者签名只覆盖 plugin.js 的后果

| 签名 | 覆盖对象 | 不覆盖 |
|:---:|:---:|:---:|
| 合集 CMS 签名 | `plugin.js` 的原始字节 | 目录数据、包容器 |
| 三层清单签名 | 各层目录文件（含展示信息、作者公钥、版本列表） | `plugin.js` |
| 作者裸签名 | `plugin.js` 的原始字节 | 展示信息、目录数据、包容器 |
| 网页 CMS 签名 | 页面入口、脚本、样式与网页清单 | 图片、字体、证书 |

因此作者签名能证明的只有一件事：插件代码与作者签署时一致。它不能证明作者可信，不能证明展示信息没被改，也不能证明包里的其他文件没被改。展示信息由合集的三层清单兜底，包容器本身没有任何签名。

离线包只带作者材料，不带合集材料，这是有意的：离线包不经过合集分发，合集签名在包内没有可校验的上下文；把合集签名塞进离线包只会制造一个无法验的字段。离线包的安装记录因此只写作者材料，不写合集证书与 CMS 签名。

## 七、未定稿

> 以下均未定稿：没有实现，也不构成承诺；每条附已排除的选项与原因。

| 方向 | 未决问题 | 已排除的选项与原因 |
|:---:|:---:|:---:|
| 给 `meta.json` 增加作者签名 | 作者是否应为展示信息负责；签名材料如何随包分发 | 由合集在生成目录数据时替作者补签——合集不能代表作者，签出来的名字是错的 |
| 离线包支持来源结论 | 离线包没有分发上下文，来源如何声明与验证 | 用包内自述的来源地址推断可信——自述字段可任意填写，等于没有约束 |
| 吊销未知态在界面区分 | 离线与在线取不到吊销列表是两种情形，是否要分开显示 | 把“未知”显示成“已吊销”——会把正常离线用户吓退，也会掩盖真正的吊销 |
| 逐材料展示三态 | 合集与作者两条路径是否各给一个状态 | 引入“部分通过”作为第四态——落盘与判定会被迫处理组合爆炸，收益只是展示更细 |
| 网页签名结论留痕 | 是否把当次结论写入设置或诊断入口 | 把网页签名结论写进安装记录——两者生命周期与归属不同，混在一处会互相污染 |

## 八、已知口径冲突

| 冲突点 | 两种说法 | 影响 |
|:---:|:---:|:---:|
| 安装验签失败是否“不可信” | 架构文档写“标记为签名失败与不可信”，实现只在吊销与恢复失败时把记录标为不可信，安装期验签失败仍视为可信 | 同一份记录，签名状态说失败、可信布尔说可信，界面若只看布尔会漏报 |
| 吊销与链失败的落盘 | 吊销会同时写进信任失败原因并置不可信；链失败写进来源结论与信任失败原因，但不置不可信 | 两种确定的负面结论在记录上的重量不同，排查时容易只看其中一个字段 |
| 锚定标记的旧注释 | 存储模块的注释仍写“证书来自信任清单”，实现已改成“链是否在本机校验通过” | 读注释会误解该字段的语义 |
| 警告的呈现样式 | 插件侧刻意用不带错误图标的普通提示，网页侧用错误样式的提示 | 同一“只警告不阻断”的语义，两种视觉强度，用户对“要不要担心”的判断会不一致 |
| 三态与四态的混用 | 文档常把签名状态与来源结论并称“校验结论” | 两个轴被压成一个词，排查时无法判断失败发生在哪一段 |
