# dsc-core 与 dsc-plugin-engine 的职责契约

> 本文负责：说明 dsc-core 与 dsc-plugin-engine 之间已经成立的职责分工、调用契约与能力粒度，记录能力清单在多处手写副本这一事实，并整理尚未落地的契约演进方向。本文不负责：插件清单字段、能力语义、限流与超时的规范条文，这些以模板仓库的 [dsc 插件运行时规范](https://github.com/omds-chat/dsc-plugin-template/blob/main/specs/plugin-runtime-spec.md) 与 [dsc 插件开发规范](https://github.com/omds-chat/dsc-plugin-template/blob/main/specs/plugin-develop-spec.md) 为准；签名链路见 [信任与签名](trust-and-signature.md)，安装与持久化见 [插件安装与存储](plugin-install-and-storage.md)，三层组件的整体视图见 [dsc 架构](../intro/dsc-architecture.md)。

## 第一部分 职责边界现状

### core 是薄门面，不是可独立部署的一层

core 不搬迁任何既有目录，而是在原位置把内核能力收敛成少量标识，只对引擎开一个入口。门面之外的东西——业务界面、会话库、API 客户端、i18n、工具函数——逻辑上属于 core，物理上保持原样：构建入口固定在应用壳，全仓用相对导入与 CSS Modules，搬迁会同时破坏导入路径、样式引用与产物路径。

门面只交出一份能力表与一对凭据，不交出 store 句柄、IndexedDB 句柄、附件原件与 API Key。core 自身不认识“插件”这个概念：它没有清单、没有生命周期、没有激活顺序，只按能力标识执行一次被授权的调用。

| 判断 | 留在 core 的理由 |
|:---:|:---:|
| 会话视图裁剪（只保留角色、文本、附件名称与大小） | 数据形状一旦流出 core 就收不回来，裁剪必须在源头做 |
| 标题长度裁剪与空标题拒绝 | 写入口只有一处，校验跟着写入口走 |
| 外源请求的协议、方法、响应类型、体积与超时 | 调用方无法放宽，约束才有意义 |
| 插件数据的键空间、64KB 配额与序列化校验 | 配额与键拼接都在 core，引擎只转发 |
| 凭证签发与票据消费 | 调用方身份与单次授权必须在被调用侧判定 |

| 不在 core 的判断 | 归属 | 理由 |
|:---:|:---:|:---:|
| 清单合法性、重名、依赖与冲突 | 引擎 | core 不认识插件，判断需要注册表 |
| 来源可信与签名结论 | 引擎 | 属于信任判定，不是内核能力 |
| 限流窗口、超时、生命周期 | 引擎 | 属于策略层，随插件策略调整 |
| 插件代码加载与恢复 | 引擎 | core 不加载代码 |

### 能力粒度是业务域级，不是统一粒度

当前能力表有十八个标识，其中十四个对插件可见，四个只给引擎管理使用。读能力按域打包，写能力按字段收敛，粒度并不齐整；这是有意的：读的边界由数据形状决定，写的边界由可回滚的最小单位决定。这十七个标识里有两项落在供应端点这条轴上，不在常规转发之列：`provider:source` 让插件声明它能提供哪些供应端点，`source:run` 是引擎按供应端点描述执行一次能力调用的唯一出口。插件侧要发起这类调用时走 `provider:run`，它不对应 core 侧的独立方法，执行由引擎选端点、读凭证后转成 `source:run`。

| 能力标识 | 粒度 | 形态 | 切在这一级的理由 |
|:---:|:---:|:---:|:---:|
| `sessions:list` | 域级读 | 会话摘要列表，不含消息 | 列表页只需要摘要，给出全文等于扩大暴露面 |
| `sessions:read` | 域级读 | 单会话只读视图，附件只留名称、大小与是否图片 | 会话是插件最常消费的整体，逐字段拆会先制造十几个标识 |
| `sessions:rename` | 字段级写 | 单个标题，裁剪到 120 字符 | 唯一的可写字段，写单位就是字段 |
| `events:session` | 单点订阅 | 只广播会话变更与当前会话 id | 事件面越窄，插件越难借此推断其他状态 |
| `notify` | 单动作 | 复用宿主文案键，不接收自由文本 | 文案与语言由宿主决定，插件不拼自然语言 |
| `settings:locale` | 单值读 | 当前语言 | 只读，且只有一个值 |
| `settings:surface` | 单点登记 + 只读面 | 激活期登记一份字段描述，宿主渲染设置表单；插件另有 `values()` 只读自身设置值 | 插件只交描述、不交控件，控件形态、样式与 i18n 归宿主；登记与校验都在引擎内完成，core 侧没有实现，与 `provider:source` 同类 |
| `ui:page` | 单点登记 + 两个回调挂载点 | 激活期登记一份声明式页面描述，宿主渲染页面；插件另可登记动作回调与数据索取处理器 | 插件只交描述、不交控件，页面形态归宿主；登记、校验与挂载点分发都在引擎内完成，core 侧没有实现，与 `settings:surface` 同类 |
| `net:fetch` | 单一动作 | 仅 https 与 GET，读文本 | 网络是最大暴露面，只保留一种受限形态 |
| `assets:read` | 单一动作，两种形态 | 仅 https 与回环地址，只读文本或字节，三态原样返回 | 资产类插件要按地址取资产包，而 `net:fetch` 只对内置插件开放；单开一条只读通道比放开通用联网面更可控 |
| `plugins:storage` | 域级读写 | 读、写、删三个成员共用一个标识 | 三者共享同一键空间与配额，拆开没有额外保护 |
| `net:fetch-post` | 单一动作 | 一次 JSON POST，响应体丢弃 | 只服务计数，不给插件可用的通用 POST |
| `plugins:data-clear` | 单一动作 | 清除单个插件全部数据 | 破坏性操作，只给宿主与引擎 |
| `chat:request` | 单点登记 | 每次请求一次的参数补丁，字段由引擎收敛 | 补丁只改请求参数，不读会话、不碰请求对象；收敛在引擎，core 只落字段 |
| `chat:request-source` | 单一动作 | 登记一个「给切片、返回补丁」的回调 | 只给引擎使用，不进入插件上下文；它是 core 在发送前回调引擎的唯一入口 |
| `provider:source` | 单点登记 | 一份供应端点描述，含协议格式、端点基址与能力清单 | 插件只交描述、不交执行代码；core 侧没有实现，登记与合并都在引擎的注册表里 |
| `provider:run` | 单一动作 | 能力标识 + 载荷，返回回流事件或模型清单 | 插件只说明「做什么」；端点选择、凭证读取与描述组装都在引擎，执行落到 core 的 `source:run`，core 侧没有独立方法 |
| `source:run` | 单一动作 | 供应端点描述 + 能力标识 + 载荷 + 凭证，返回回流 | 只给引擎使用；凭证与描述都由引擎在执行时给出，插件拿不到这两项；插件侧的入口是 `provider:run` |

由此可以看出“业务域级能力”的实际含义：授权单位是域，数据形状由 core 定义，插件拿到的是裁剪后的视图而不是内核对象。它同时也是“原子积木”方向的起点——现有读能力偏粗，写能力偏细。

### 按供应端点执行：能力维度的第二条入口

这一条入口的对象是「供应端点」（provider endpoint）：插件声明、宿主调用的模型端点，与插件安装来源（`inner`、`outer` 等）不是一回事，文档与界面因此不用「来源」这个词，免得与市场的来源混读。

core 原本只按「插件能力」执行，识别的是数据形状（会话、资产、插件数据）。新增的 `source:run` 换成另一个维度：调用方给一份供应端点描述、一个能力标识与载荷，core 内部按描述的 `format` 组装请求、按 `format` 解析回流，全程不认识厂商。描述里的 `capabilities` 与能力标识是同一套词表，core 在执行前先判定这份描述是否声明了这项能力。

能力表九项，只有两项已经落地，其余七项只有标识、载荷形态与一句 TODO，执行时按 `unsupported` 拒绝。

| 能力标识 | 形态 | 已落地 | 说明 |
|:---:|:---:|:---:|:---:|
| `text.generate` | 流式回流 | 是 | 组装一轮对话请求；回流折成文本、思考、标题与结束四类事件 |
| `models.list` | 一次性结果 | 是 | 读模型清单，只取 id |
| `reasoning.think` | 流式回流 | 否 | 思考过程单独成能力，供只想要思考的调用方使用 |
| `vision.image` | 流式回流 | 否 | 图片输入与文本回流 |
| `document.read` | 一次性结果 | 否 | 文档输入转文本 |
| `audio.asr` | 一次性结果 | 否 | 音频转文本 |
| `audio.tts` | 二进制回流 | 否 | 文本转音频 |
| `tool.web-search` | 一次性结果 | 否 | 一次查询与结果条目 |
| `tool.read-url` | 一次性结果 | 否 | 按地址取回正文 |

五条取舍：

- 厂商知识压进 `format`，不进 core 的分支：描述只声明协议格式，端点路径按格式推导，单项可用 `endpoints` 覆盖。新增一家厂商等于新增一份描述，core 的分支只按格式与能力走。
- 凭证不进描述：描述是插件交的，也会被界面展示，凭证不能出现在那里。凭证存在引擎的 IndexedDB 里，只有执行时由引擎读出，随这一次调用交给 core；core 不持久化，也不把它放进任何回流事件。
- 不让插件交执行代码：交执行代码等于把组装与解析搬到插件侧，请求形态与回流形状就不再由内核定义，凭证也会落到插件手里。
- 基址先规范化再比较与执行：去首尾空白、主机转小写、去默认端口、去尾斜杠，带 query、hash 或内嵌用户名密码的地址直接拒绝。注册表的定义比对与执行期的地址拼接只看规范化后的字符串；否则同一份描述写两遍格式就会拼出非法地址。
- 协议与主机的放行范围是宿主的策略，不是插件可申请的权限：默认只接受 https 与回环地址的 http；设置里的「允许局域网 http 供应端点」打开后，供应端点校验额外放行私有网段与其它非回环主机的 http。放行开关属于用户决策，端点描述里没有对应字段，插件也不能把这一项申请进清单。

已落地的两项与既有 DeepSeek 发送路径逐字段一致：`text.generate` 打到 `/anthropic/v1/messages`，`models.list` 打到 `/models`，请求体字段、请求头与流式解析沿用同一份实现。描述的形态检查（id、展示名、格式、基址、能力清单、端点覆盖）只有一份实现，引擎与插件入口共用。

### 放行边界：只有供应端点读这份策略

基址判定的默认口径没变：`isHttpsOrLocalUrl` 与 `normalizeSourceBaseUrl` 在不传策略时仍是「https 任意主机，http 仅回环地址」。`net:fetch`、`net:fetch-post`、`assets:read`、插件产物地址、插件市场来源与计数接口都继续走默认口径，局域网 http 开关不会放宽它们；共用的判定函数改成带可选策略参数的形式，只有供应端点这条通道显式传入策略，避免某天给别的通道传参时误放宽。

策略的读取点有三处，取同一个开关：

| 读取点 | 位置 | 作用 |
|:---:|:---:|:---:|
| 声明 | 引擎注册表登记前 | 开关关闭时局域网 http 的描述按 `baseUrl` 拒绝，不入表 |
| 凭证 | 引擎凭证库读写 | 基址规范化与键拼接用同一策略，否则开关打开后仍读不到该端点的 Key |
| 执行 | core 的 `source:run` 入口 | 每次执行按当前开关重新判定基址；开关在声明之后被关闭时，老声明仍在注册表里，但执行链路的基址校验与凭证读取都会失败，请求不会发出 |

开关关闭时行为与改动前完全一致；开关打开时也不保证请求一定发得出去：页面为 https 时浏览器会直接阻断对局域网 http 的混合内容请求，因此这条通道只适用于本地开发或 http 页面。宿主不为此生成或替换任何证书，也不把该开关扩散成通用的 http 放行。

### 执行链路：从插件调用到回流

插件侧只有一个入口 `context.provider.run(capability, payload)`，清单需要申请 `provider:run`；引擎侧把它拆成四段，每段的归属都是确定的：

| 段 | 归属 | 做的事 | 能给出的错误码 |
|:---:|:---:|:---:|:---:|
| 选端点 | 引擎（`sources.ts`） | 取该能力在注册表里的第一个端点；本版不做用户选择 | `capability-unavailable` |
| 读凭证 | 引擎（`credentials.ts`） | 按「端点 id + 规范化后的基址」读取，读到 `stale` 直接拒绝 | `credential-missing`、`credential-stale` |
| 执行 | core（`source:run`） | 校验描述是否声明该能力、规范化基址，再组装请求并解析回流（当前只有 Anthropic 兼容协议的实现） | `capability-unavailable`、`endpoint-unreachable`、`protocol-error` |
| 归类 | 引擎（`providerRun.ts`） | 把 core 与协议层的失败折成插件可判定的错误码，原文留在 `detail` | `credential-rejected`、`protocol-error` |

四处取舍：

- 选端点先于读凭证。端点选择只看注册表，与凭证是否已填无关；缺凭证时报 `credential-missing`，不换到下一个端点——静默换端点会让「请求打到了哪里」变成隐式状态。
- 本版固定取第一个端点。注册表按声明顺序入表，同一序列下选中结果稳定；用户选择尚未落地，落地时只需替换「选中」这一步，插件侧的调用形态不变。
- 未接通的能力先拒后读。`text.generate` 与 `models.list` 之外的七项在选端点与读凭证之前就按 `capability-unimplemented` 拒绝，不触碰用户的 Key，也不发请求。
- 选中的端点是全局的。执行只认注册表，不区分由哪个插件声明：任何拿到 `provider:run` 的插件都能在别的插件声明的端点上发起调用。本版接受这一点，因为端点选择尚未交给用户；一旦做选择，必须同时决定「可选集合按插件限定」还是「由用户明确指定这次用哪个端点」，否则归属问题会随端点数量增长而放大。

回流是惰性的：`text.generate` 的调用立刻返回一个事件流，鉴权与网络失败发生在第一次迭代，因此错误归类必须覆盖迭代期，而不只是包住调用本身；`models.list` 一次性返回，失败在调用时抛出。两者共用同一张错误码表：

| 错误码 | 含义 | 归类依据 |
|:---:|:---:|:---:|
| `credential-missing` | 没有该「端点 id + 基址」的凭证记录，或凭证存储读不出来 | 凭证存储的读取结论，或 core 的凭证拒绝 |
| `credential-stale` | 同一端点 id 存在别的基址的记录，端点换过主机 | 凭证存储的读取结论 |
| `credential-rejected` | 端点以 401 或 403 拒绝凭证 | 协议层状态码 |
| `capability-unavailable` | 没有端点提供该能力，或选中的端点未声明它 | 注册表，或 core 的能力判定 |
| `capability-unimplemented` | 端点声明了该能力，本版尚未接通 | 引擎的能力落地表，或 core 的 `unsupported` |
| `endpoint-unreachable` | 请求没有拿到响应：网络层失败，或端点基址不可用 | 协议层的网络失败，或 core 的基址判定 |
| `protocol-error` | 拿到响应但不符合协议：非 2xx、非流式响应、JSON 不合法、流提前结束 | 协议层的其余失败，以及无法归类的失败 |

失败不吞：每一次失败都抛 `PluginProviderRunError`，`code` 是判定依据，`detail` 保留原文，`capability` 与 `sourceId` 标明是哪条调用；凭证不进错误、结果与回流事件。`credential-rejected` 单列一码而不并入 `credential-missing`：前者要用户核对 Key，后者要用户先填 Key。

### 未决期：先声明的那份临时生效

冲突判定只看 `format`、规范化后的 `baseUrl` 与 `endpoints` 三项：这三项决定请求发到哪里、按什么协议组装。`label` 只是展示名，差异不算冲突，展示名取先声明方；能力清单按并集合并，也不参与判定。

同一端点 id 的两份描述在这三项上不一致时，注册表判冲突并打标记，但不把该 id 从表里摘掉：先声明的那份继续生效，后声明的那份不生效，两份都留在声明里，`owners` 把冲突方也记进去，因此「谁还声明过这个 id」在冲突期也查得到。

这么做的代价是明确的：

| 代价 | 说明 |
|:---:|:---:|
| 执行可能打到不是自己声明的那台主机 | 后声明方的插件看到 id 在表里，但它声明的端点没有生效，执行期只认先声明方的基址 |
| 冲突方的能力不进矩阵 | 能力并集只对定义一致的声明生效，冲突方声明的能力在冲突解决前不会被看到 |
| 冲突是需要展示的状态 | 冲突不阻断激活与执行，只体现在注册表视图与引擎日志里，界面必须主动展示，否则等于没有标记 |
| 冲突方退出会改变结论 | 先声明方退出后，原本冲突的下一份声明重新成为唯一定义，界面上的「生效端点」会随之改变 |

不采用「冲突时该 id 不进表」的理由：那样一来先声明方的合法端点会被第三方的错误声明一起拖下水，冲突方退出后还要重新判定谁该生效；当前做法保证「谁在生效」始终有确定答案，代价是把冲突标记当成必须展示的状态来维护。

### 凭证与票据：两层，不是一层

| 交付物 | 形态 | 生命周期 | 证明什么 |
|:---:|:---:|:---:|:---:|
| 凭证 | 只在 core 内部可验证的符号令牌，带持有者标记 | 引擎启动时申请一次，全程复用 | 调用方是引擎 |
| 票据 | 绑定单一能力标识的编号 | 每次转发签发一张，5 秒内消费，消费即作废 | 这一次调用被允许 |
| 绕过事件 | 能力标识、原因、时间 | 保留最近 50 条 | 有人试过不走门面 |

三个取舍：

- 用符号令牌而不是布尔标记：同进程内的模块都能改写布尔字段，符号令牌不能跨 realm 伪造，伪造者拿不到同一个符号。
- 每次调用都签票据：票据把“这一次”与“单一能力”绑定，一张票据不能挪给另一个能力用，也不能重复使用。
- 票据窗口只覆盖签发到消费：它不承担会话有效期，也不承担“引擎还活着”的判断，引擎存活由应用生命周期保证。

凭证能约束的是“走门面的路径”，不是进程隔离。core 还导出宿主侧的数据管理入口（列举、查询、清除插件数据），这些入口不经凭证门面，供设置界面的数据管理直接调用；引擎自己也直接引用其中的查询函数判断卸载后是否遗留数据。这一点是“唯一 core 通道”方向要处理的现状。

### 引擎是 1:1 转发加门控

引擎为每个插件构造一个上下文对象。成员调用时的顺序固定：清单授予判定、限流窗口、取消检查、超时包装、签发票据、core 验凭证与票据。引擎不缓存会话、不聚合数据、不拼装业务视图，也不直接读写聊天历史库。

表中的「挂载点判定」指：挂载点是插件声明要挂到宿主哪个回调位置，插件登记处理器前先核对该位置是否写在清单的 `mounts` 里。

| 上下文成员 | 能力标识 | 门控 | 转发形态 |
|:---:|:---:|:---:|:---:|
| `sessions.list` | `sessions:list` | 授予、限流、超时 | 一次调用 |
| `sessions.read` | `sessions:read` | 授予、限流、超时 | 一次调用 |
| `sessions.rename` | `sessions:rename` | 授予、限流 | 一次同步调用 |
| `events.on` | `events:session` | 授予、挂载点判定、限流（仅登记） | 登记处理器，不逐次调用；每次登记占一个限流名额 |
| `ui.notify` | `notify` | 授予、限流 | 一次同步调用 |
| `settings.locale` | `settings:locale` | 授予、限流、超时 | 一次调用 |
| `settings.register` | `settings:surface` | 授予、限流（仅登记）、描述形态检查 | 登记一份字段描述，返回释放函数，停用随引擎清理；core 侧没有对应实现，校验与注册表都在引擎内 |
| `settings.values` | `settings:surface` | 授予、限流 | 一次同步调用，只读自身命名空间；覆盖值优先，否则默认值，secret 字段不返回 |
| `ui.registerPage` | `ui:page` | 授予、限流（仅登记）、描述形态检查 | 登记一份声明式页面描述，返回带页面 id 的句柄，停用随引擎清理；core 侧没有对应实现，校验与登记表都在引擎内 |
| `ui.onPageAction` | `ui:page` | 授予、挂载点判定、限流（仅登记） | 登记页面动作回调；用户点击页面动作按钮时由引擎同步回调一次，载荷带页面 id、动作键与可选的条目键和表单草稿值 |
| `ui.onPageData` | `ui:page` | 授予、挂载点判定、限流（仅登记） | 登记页面数据处理器；宿主进入页面或动作返回刷新指示时由引擎同步索取当前模型，非法返回值回落到登记时的缺省模型 |
| `net.getText` | `net:fetch` | 授予、限流、内置限定、超时 | 一次调用 |
| `net.postJson` | `net:fetch-post` | 授予（按 `net:fetch`）、限流、内置限定、超时 | 一次调用 |
| `assets.readText`、`assets.readBytes` | `assets:read` | 授予、限流、超时 | 一次调用；两个成员共用一个标识 |
| `storage.get`、`set`、`remove` | `plugins:storage` | 授予、限流 | 一次同步调用，按操作区分 |
| `chat.onBeforeRequest` | `chat:request` | 授予、挂载点判定、限流（仅登记） | 登记处理器；每次请求前由 core 回调一次，带 10 毫秒预算 |
| `provider.registerSource` | `provider:source` | 授予、限流（仅登记）、描述形态检查 | 登记一份供应端点描述；core 侧没有对应实现，合并与冲突判定都在引擎注册表里 |
| `provider.run` | `provider:run` | 授予、限流、超时 | 选端点、读凭证、调 `source:run`；`text.generate` 的回流由调用方惰性消费，`models.list` 一次性返回 |

“1:1”指的是调用链一一对应，不是成员与能力标识一一对应。四处例外值得记住：

- 事件只在引擎启动时向 core 订阅一次，之后由引擎按挂载点分发给各插件；插件登记处理器不产生 core 调用。
- 插件数据的三个成员共用一个能力标识，core 侧按操作字段分派。
- 计数请求用独立的能力标识与独立限流窗口，但授予口径仍按 `net:fetch`，插件清单无法单独申请它。
- 资产读取的两个成员共用一个能力标识，core 侧按形态分派实现；读取结果的三态不是异常，`status` 与 `no-status` 都按返回值交给插件，只有引擎侧能确定的拒绝才抛错。
- 请求前补丁的调用方向是反的：插件只在引擎里登记处理器，core 在发请求前主动回调引擎取补丁。core 侧因此多了 `setRequestPatchSource` 一个入口，插件侧则完全不接触 core。

引擎自有的职责不经过 core：生命周期状态机、同一插件的操作串行化、安装与恢复、插件日志与引擎日志、内置插件 id 集合。这些职责没有对应的能力标识，也不打算变成能力——它们约束的是引擎自身，不是插件能申请的东西。

### 冲突处置：引擎自有的保守策略

插件清单的 `conflicts` 在两条时点上生效，判定都在引擎，core 不参与：

| 时点 | 判定口径 | 结论 |
|:---:|:---:|:---:|
| 安装期（`installConflicts.ts`） | 新清单与全部已安装记录比声明方向：本插件声明排斥对方、对方声明排斥本插件、两边都声明合并为 mutual；已安装记录不论启停都参与 | 拒绝安装，原因按声明方向分三条（`install-conflict-declared`、`install-conflict-required`、`install-conflict-mutual`） |
| 启用期（`activationConflicts`） | 只看 `active` 记录 | 不只拒绝：冲突涉及的全部启用插件先停用，整组冲突写入待决定记录，由用户选择保留哪一个 |

安装期两条入口共用同一份判定：在线安装 `installFromUrl` 与本地离线包提交都经过注册表的 `checkInstallable`，反向声明（已安装插件排斥新插件）在两条入口上都拦得下来，不存在「市场装得进、离线装不进」之类的口径差。恢复既有记录不判安装期冲突：按冲突拦下等于把用户的插件丢掉，共存的冲突交给启用期处置。

待决定记录是引擎自有的持久化状态（`pendingConflicts.ts` 与插件库的 `conflict-groups` 仓库），core 无感知。语义上有四条边界值得记住：

- 引擎不替用户选边：检测到冲突先把涉及的启用插件全部停用，选择之前不自动启用任何一方；启动恢复时即使落盘的期望标记是启用，待决定涉及的插件也一律不自动启用。
- `resolvePendingConflict(groupId, keepId)` 先删记录再按选择启用保留方：启用失败时该组不再待决定，失败原因照常提示；其余保持停用，不连带启用依赖保留方的插件。
- 记录里的插件卸载后整对失效：卸载与启动恢复共用同一份按已安装集合的修剪，「保留哪一个」已无从选择。
- 记录读取时按冲突对重建组 id 与插件清单，旧记录里两者与冲突对不一致不会让同一组散成两条。

## 第二部分 能力清单的手写副本

### 现状

能力表在仓库内有多处结构副本。副本不全是坏事：有的是类型约束要求的，有的是文案要求；问题在于它们之间没有机械同步，新增一项能力需要手工改齐。

| 位置 | 形态 | 是否受类型约束 | 漂移后的表现 |
|:---:|:---:|:---:|:---:|
| `dsc-core/types.ts` 的能力联合与 `CORE_CAPABILITIES` 数组 | 唯一权威的“插件可见集合” | 数组元素受联合约束，但联合新增成员不会强制数组补齐 | 漏项时仍能编译，下游表现为“未知能力” |
| `dsc-core/registry.ts` 的服务类型表 | 十三个标识到实现签名的映射（`chat:request`、`provider:source` 与 `provider:run` 在 core 侧没有实现，不进该表） | 是，增加成员会编译失败 | 实现签名不一致时编译失败 |
| `dsc-core/index.ts` 的注册块与门面方法 | 十三个注册、十六个包装方法（`settings:surface`、`ui:page` 与 `chat:request`、`provider:source`、`provider:run` 同类，core 侧没有实现） | 否 | 新增能力要手写注册与包装，容易只改一半 |
| `dsc-plugin-engine/capabilities.ts` 的策略表 | 十七个标识的限流与异步成员的超时 | 限流字段由 `Record` 强制补齐；超时字段可选，同步成员不填 | 数值与文档分叉 |
| `dsc-core/source-catalog.ts` 的供应端点能力常量表与能力联合 | 九个供应端点能力标识的唯一权威表 | 常量表用 `satisfies` 约束取值，数组本身不受联合约束 | 联合新增成员时数组不报错，漏项表现为「端点未声明该能力」 |
| `dsc-plugin-engine/sources.ts` 的供应端点注册表 | 声明合并、定义比对与能力矩阵的唯一实现 | 矩阵按能力表逐项建键 | 冲突字段集合与文档分叉时不会报错 |
| `dsc-plugin-engine/requestPatch.ts` 的字段上限 | 六个补丁字段的范围与长度 | 否 | 与两处组件说明、插件文档分叉 |
| 引擎的上下文构造 | 十七个成员到能力与实现的映射（`settings:surface` 一个标识对应 `register` 与 `values` 两个成员，`ui:page` 一个标识对应 `registerPage`、`onPageAction` 与 `onPageData` 三个成员） | 否 | 成员增删要同时改上下文类型与构造 |
| `dsc-market/client.ts` 的能力声明解析 | 复用 `CORE_CAPABILITIES` 校验 | 是 | 已收敛，未产生副本 |
| `dsc-plugin-engine/localPackage.ts` 的能力声明解析 | 只校验字符串形态，不校验白名单 | 否 | 未知能力延迟到提交阶段才拒绝 |
| 两处组件说明与架构文档 | 表格 | 否 | 与代码不同步时无告警 |
| 模板仓库的两篇规范 | 外部表格 | 否 | 跨仓库同步只能靠规范维护流程约束 |

### 类型能兜住什么，兜不住什么

- 能兜住映射完整性：策略表与服务类型表用 `Record` 或映射类型声明，漏一个标识会编译失败。
- 兜不住集合成员该不该存在：插件可见集合是一个手写数组，联合类型新增成员时数组不会报错。这个缺口最危险，因为失败是静默的。
- 兜不住策略数值与文案一致：限流上限、单次超时、插件可见形态这三类信息散在代码、两处组件说明与模板规范里。
- 兜不住两条安装路径的口径：市场侧解析能力声明时会校验白名单，离线包预检只校验字符串形态，同一份 `meta.json` 在两条路径上的结论时机不同。

### 改动面

新增一项对插件可见的能力，最小改动面是：能力联合、可见集合数组、服务类型表、服务注册、门面包装方法、引擎策略表、引擎上下文构造，以及两处组件说明与模板规范。其中前两项在同一文件，其余分布在三个文件与两处文档。这是当前的事实，也是下一部分几条方向共同的出发点。

`chat:request` 的落地补了一条反例：它在 core 侧没有实现，因此服务类型表与服务注册都不必补齐，但策略表与上下文构造仍要各加一项，能力联合与可见集合数组仍要各加一项。也就是说，改动面的大小取决于这项能力是否有 core 侧实现，而“是否需要 core 侧实现”这件事本身没有类型约束兜底——漏判的表现是 core 侧多一个空实现，或者引擎登记了一个永远不会被调用的服务。

`assets:read` 的落地补了第二条样本，改动面比前两条都长：它在 core 侧有实现，但两个上下文成员共用一个能力标识，因此服务注册一处、服务类型表一项、门面方法两个；策略表与上下文构造各一项，能力联合与可见集合数组仍各一项，另外还多出「首次使用来源」的去重状态与一条文案键。标识只多一个，当时门面方法从十三个变成十五个——包装方法数与能力标识数进一步脱钩。三态结果没有扩大改动面：它只是返回值形状，不新增错误类型表、不新增策略字段；代价转移到插件侧，插件必须同时处理三态返回值与 `PluginAssetError`。真正没有机械同步兜底的仍是能力联合、可见集合数组、策略表、上下文构造与两处组件说明这五处，模板规范的同步不在本仓库的校验范围内。

`provider:source` 与 `source:run` 的落地补了第三条样本，两半的分布并不相同：`provider:source` 与 `chat:request` 同类，只在能力联合、可见集合数组、策略表与上下文构造各加一项，core 侧不留空实现；`source:run` 与 `assets:read` 同类，service 类型表、服务注册与门面方法各加一项，但它不进可见集合，插件清单申请它按未知能力拒绝。两个标识合计，改动面是能力联合两项、可见集合一项、服务类型表一项、服务注册一项、门面方法一项、策略表两项、上下文成员一项。

`provider:run` 的落地补了第四条样本，形态与 `chat:request`、`provider:source` 一致：能力联合、可见集合数组、策略表与上下文构造各加一项，core 侧不留空实现。多出来的部分只在引擎内：端点选择、凭证读取与错误归类合成一个独立模块（`providerRun.ts`），它不扩大上面那条改动面，但把「插件侧入口」与「core 侧执行」之间的转换显式写进了代码，测试夹具也因此可以只替换执行入口、不建 core 门面。

`settings:surface` 的落地补了第五条样本，改动面与 `provider:source` 同类：能力联合、可见集合数组、策略表与上下文构造各加一项，core 侧不留空实现；多出来的部分在引擎与宿主侧——描述校验、注册表与值读写门面合成独立模块（`pluginSettings.ts`），设置覆盖值的存储落在 dsc-core 的新宿主侧入口（`plugin-settings.ts`，不经凭证门面，与数据管理入口同法），secret 字段复用凭证库，宿主另渲染详情页表单。一个标识对应两个上下文成员（`register` 登记、`values` 只读），与 `assets:read` 一项对应两个门面方法的情况同形。

`ui:page` 的落地补了第六条样本，改动面与 `settings:surface` 同类：能力联合、可见集合数组、策略表与上下文构造各加一项，core 侧不留空实现；多出来的部分在引擎与宿主侧——页面描述校验、登记表与动作、数据两个挂载点的处理器登记合成独立模块（`pluginPages.ts`），挂载点联合与挂载点表各加两项（`ui:page-action`、`ui:page-data`），宿主另在会话视图列表里给每个页面一个入口，并在主区渲染页面区块渲染组件。一个标识对应三个上下文成员（`registerPage` 登记、`onPageAction` 与 `onPageData` 两个回调登记），三个成员全部是登记型同步调用，回调由引擎发起、不占限流名额。

供应端点侧另有一条独立的标识轴：九个端点能力标识有自己的一份常量表与联合类型，与核心能力标识不共用词表。它们不进入插件清单，只在供应端点描述的能力清单里出现，因此不扩大上面那条改动面；代价是多一处需要手工同步的副本，已记在上表中。

## 第三部分 尚未落地的方向（未定稿）

> 本节整体未定稿：没有任何实现，不构成接口承诺，任一条都可能被整体放弃或换一种做法。每条只记录意图、与现状的差距、尚未决定的问题，以及已经排除的选项与原因。

### 3.1 原子积木（未定稿）

意图：把业务域级的读写拆成更小的可判定单元，让授权粒度贴近数据粒度，例如只读会话标题、只读消息文本、只改标题，而不是“读整个会话”。

与现状的差距：现在 `sessions:read` 一次给出会话摘要、全部消息文本与附件描述；拆分需要 core 侧新增多个视图与对应的裁剪规则，并把限流窗口、超时与文档一起重排。能力数量会明显上升，策略表的维护成本随之上升。

未决问题：拆到什么程度算“原子”；拆分后向量是“按字段授权”还是“按字段返回”；限流窗口按标识各自计数会不会让调用预算碎片化；模板规范与仓库文档的同步节奏如何安排。

已排除的选项：把完整会话交给插件、由插件自行过滤——等于把裁剪责任移出 core，数据形状再也收不回来。

### 3.2 组合能力（未定稿）

意图：在原子积木之上定义可命名的组合（能力包或角色），安装时按组合声明，一次授予一组原子能力，避免清单逐项罗列。

与现状的差距：现在只有一张扁平的能力集合，清单只能逐项列举，没有组合层，也没有“授予预设”的概念。

未决问题：组合是否带版本；组合与单项限流如何叠加；组合能否由插件自定义；组合变更是否算清单变更、要不要重新走安装校验。

已排除的选项：用通配符表达组合（形如“某个域下的全部能力”）——无法在安装期静态确定授予面，与“未知能力一律拒绝”的口径直接冲突；在运行时用角色字符串展开——安装期校验需要确定的集合，展开发生在运行时等于把校验推后。

### 3.3 唯一 core 通道（未定稿）

意图：内核能力只有一条可达路径，即引擎持凭证与票据走门面；插件、宿主界面与引擎内部都不得旁路。

与现状的差距：门面之外仍有宿主侧的数据管理入口，不经凭证；卸载流程用到的数据查询也走这些入口。凭证约束的是“经门面的调用”，不是“所有能拿到 core 的代码”。

请求前补丁沿用了同样的例外，并且多出一层：登记来源走凭证与票据（`chat:request-source`），但 core 在发请求前调用来源时不签票据，也不检查调用次数。这是有意的最小实现——回调发生在一次请求的中途，换一次票据只增加延迟而不增加约束；代价是“唯一通道”在反方向上仍然没有可审计的凭据。

未决问题：宿主侧入口要不要也纳入票据体系（需要一种“宿主”身份的凭证，且要区分界面与引擎）；数据管理这类批量操作是否适合逐次签发；反方向的回调（请求补丁）要不要也带凭据；迁移期间如何避免同一能力出现两套调用形态。

已排除的选项：用 import 图当隔离边界——打包后所有模块在同一个执行环境里，import 关系不构成运行时约束；给插件暴露内核接口再用文档约定约束——约定无法在运行时拒绝调用。

### 3.4 运行时能力声明（未定稿）

意图：插件在激活时声明实际需要的能力子集，引擎按“清单声明与运行时声明的交集”授予，没声明的不授予，从而把“安装时申请”和“运行时实际使用”分开。

与现状的差距：清单能力在安装期固定，上下文一次性构造，没有运行时收紧机制；能力授予只有“清单里有”与“没有”两种状态。

未决问题：交集为空时是拒绝激活还是允许（会得到一个什么都不能做的插件）；停用再激活是否重新声明；声明是否只允许发生在激活入口内；交集与限流窗口如何对应。

已排除的选项：允许运行时申请清单之外的能力——等于把安装期校验作废，用户确认过的范围会被悄悄扩大；让插件自行构造上下文成员——上下文必须由引擎构造，否则门控只剩文档。

### 3.5 引擎 API 版本轴（未定稿）

意图：引擎对插件暴露的上下文与生命周期契约有独立的版本号，与产品版本解耦；清单里的兼容范围针对这条轴，而不是针对产品版本。

与现状的差距：当前只有一个核心版本常量，它同时充当产品版本、能力表版本与兼容性比较基准；引擎对外报出的版本直接复用该常量。产品修订一次，所有插件的兼容判定都要跟着重算，而契约可能根本没变。

未决问题：需要一条还是两条轴（core 能力表一条、引擎契约一条）；兼容判定是否仍用单段范围表达式；旧的兼容字段如何迁移，迁移期两条轴如何并存。

已排除的选项：继续用产品版本号兼作契约版本——产品版本的迭代节奏与契约变更不同步，一次产品修订会让全部插件重新判定；用日期或构建哈希当版本——不可比较、不可读，也无法写进清单的兼容范围。

### 3.6 已排除的横向做法

| 做法 | 排除原因 |
|:---:|:---:|
| 直接对插件字节做落盘文本替换 | 插件产物按原始字节签名，替换会改变字节、让合集签名与作者签名同时失效，也让“存储文本可还原”的前提不成立；把门控寄托在字符串替换上，等于用文本匹配代替运行时授权，绕过方式不可枚举 |
| 用压缩或编码后的形态存储插件代码 | 恢复时要还原成与签名时一致的字节，多一层编码就多一处不一致风险，收益只是省存储 |
| 用 `trusted` 布尔承载来源结论 | 一个布尔装不下“链不通过”“吊销”“缺证书”“未校验”四种情况，判定会被压平；现状已把它降级为旧记录兼容字段 |
| 把能力表下发给插件自行判定 | 判定必须在被授予侧，交给申请方等于取消门控 |
| 由引擎缓存会话或聚合数据 | 缓存会让“读到的数据”与“内核当前状态”分叉，也让权限随时间漂移 |

## 已知口径冲突

| 冲突点 | 两种说法 | 影响 |
|:---:|:---:|:---:|
| 能力数量的读法 | “十七个能力标识”与“前十三个在核心能力表内”并存，可见集合实际是十三个、联合类型是十七个 | 读者容易把可见集合当成完整表，新增能力时漏改数组也不报错 |
| core 侧实现的条数 | 服务类型表十三个、门面方法十六个，而联合类型十八个：`chat:request`、`provider:source`、`provider:run`、`settings:surface` 与 `ui:page` 没有 core 侧实现，`assets:read` 一项对应两个门面方法 | 数条数时容易把几个数字当成笔误，而不是“是否需要在 core 侧落地”与“一项能力对应几个成员”的判断结果 |
| 两套能力标识 | 核心能力标识用冒号（`sessions:read`），供应端点能力标识用点号（`text.generate`），两者不是同一张表 | 混用时容易把端点能力写进插件清单，或把核心能力当成端点能力去执行 |
| 资产读取的失败表达 | 三态返回值与 `PluginAssetError` 并存 | 插件要同时处理返回值与异常，文档必须写清哪类失败走哪条路，否则会漏掉一种 |
| 引擎报出的版本 | 文档称其为版本，实现里等于核心版本常量与产品版本 | 契约版本与产品版本无法区分，兼容判定基准含糊 |
| 能力白名单校验 | 市场侧解析能力声明时校验白名单，离线包预检只校验字符串形态 | 同一份声明在两条安装路径上的拒绝时机不同 |
| 宿主侧数据入口 | 文档强调“唯一出口”，实现仍保留不经凭证的宿主入口 | “唯一通道”目前只是门面内的性质 |
