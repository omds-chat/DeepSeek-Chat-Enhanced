# 文档索引

本索引登记 `docs/` 下的全部正文、根目录说明文档与组件说明文档,一份一行。列含义: 职责一句话说明该文档负责什么;主要内容列出可检索的主题;什么时候需要读给出触发场景;主要读者是首要受众。

文档分四类: 面向产品用户的使用指南、面向插件开发者的开发文档、面向维护者的设计文档,以及指向模板仓库规范的占位文档。规范正文不在本仓库维护,指针关系见「文档分层」。

## 文档分层

四类文档各有读者与权威度,混读会得出相互矛盾的口径:

| 层 | 包含文档 | 主要读者 | 与规范正文的关系 |
|:---:|:---:|:---:|:---:|
| 用户使用指南 | `user/guide/index.md`、`user/guide/plugins.md` | 产品用户 | 只描述界面上的可见行为,不引规范条文 |
| 插件开发者文档 | `user/develop/index.md`、`user/develop/basic/` 五篇、`user/develop/framework/build-a-plugin.md` | 插件开发者、合集维护者 | 契约条文以模板仓库 `dsc-plugin-template` 的 specs 为准;本仓库只承担指针,以及签名、验签、版本继承、安装持久化这些 dsce 专有机制的说明 |
| 维护者设计文档 | `design/core-engine-contract.md`、`design/plugin-install-and-storage.md`、`design/trust-and-signature.md`、`design/side-branches.md`,以及 `intro/dsc-architecture.md`、`intro/dsc-diff-dsh.md` | 维护者 | 记录已成立的契约现状、理由与未定稿方向,不定义对外条文,也不构成承诺 |
| 指向模板仓库的占位文档 | `user/develop/basic/plugin-develop-spec.md`,以及 `plugin-product-spec.md` 的前半部分 | 插件开发者 | 只保留指针、迁移说明与「已迁往模板」对照,正文在模板仓库 |

规范正文的归属需要单独交代:

- 插件清单字段、校验顺序、版本与依赖、运行时 meta、产物形态、导出契约、生命周期、能力与限流、离线包布局,正文都在模板仓库 `dsc-plugin-template` 的 `specs/plugin-develop-spec.md` 与 `specs/plugin-runtime-spec.md`;清单与运行时 meta 的 JSON Schema 与零依赖校验脚本同样在模板仓库。
- 本仓库保留指针的两篇占位文档不重复维护上述内容,只补 dsce 专有部分: 合集签名、三层清单与目录数据校验、来源结论、安装记录持久化、引擎安装接口、错误与降级。
- `trust-chain.md`、`web-signature.md`、`page-version-inherit.md` 属于本仓库自有机制,模板仓库没有对应正文。
- 仓库主 README 与组件 README 是自述与实现说明,不属于上述四层;它们对插件契约的表述服从模板仓库规格。

## 冲突时以谁为准

优先级从高到低: 脚本与实现 > 模板仓库规范 > 本仓库文档 > 设计文档。

| 顺序 | 依据 | 生效范围 | 落到本文档体系中的做法 |
|:---:|:---:|:---:|:---:|
| 1 | 脚本与实现: `scripts/pki/` 下的签发与签名脚本、`rspack.config.ts` 的构建期注入、`src/services/` 与 `src/components/` 的运行时逻辑 | 任何描述与代码不一致的地方 | 以代码为准;多篇机制说明已在开头声明与哪几个实现对齐、未实现的能力不写入正文,发现偏差时改文档而不是改口径 |
| 2 | 模板仓库规范: `dsc-plugin-template` 的 `specs/plugin-develop-spec.md`、`specs/plugin-runtime-spec.md` 与其 Schema、校验脚本 | 插件清单、产物形态、运行时契约、离线包布局 | 两篇占位文档与设计文档的「不负责」段落均把这类主题指向模板仓库;本仓库不再给第二版说法 |
| 3 | 本仓库文档: 使用指南、开发文档的非占位部分、主 README 与组件 README | 界面行为、签名体系、验签、版本继承、安装与降级 | 同一主题出现两种说法时,以对齐实现更紧的一篇为准,并把结论回写到另一篇,不留并存口径 |
| 4 | 设计文档: `design/` 四篇与 `intro/` 两篇 | 现状解读、取舍理由、演进方向 | 「已知口径冲突」与「未定稿」两段是显式登记的分歧,不作为规范依据;取舍确定后先改实现与脚本,再回写设计文档 |

两处需要特别注意:

- 设计文档的「已知口径冲突」把同一件事的两种说法并列,是为了留痕而不是让读者二选一;判断当前事实一律以脚本与实现为准。
- 签名相关文档之间,签发与分发的操作口径看 `trust-chain.md`,运行时如何呈现结论看 `trust-and-signature.md`,两者冲突时仍按上表逐级回退。

## 维护约定

- 新增、改名或删除 `docs/` 下的 md 时,同时更新本索引与 `docs/index.html`(文档入口静态页),两份入口列出的文档集合保持一致。
- 层内索引与本索引是上下两级: 新文档先在所属层的 `index.md` 登记,再在本表补一行;本表只列文档,不复制层内说明。
- 模板仓库已覆盖的主题不在本仓库复制正文,只在占位文档增加指针与「已迁往模板」对照行;迁移完成后原文的细节若已由模板承接,本仓库不保留第二份副本。
- 设计文档只在契约或取舍变化时更新;「未定稿」条目落定后,先改实现与脚本,再回写文档并移出未定稿段落。
- 版本文档只保留本地快照与待办,不随仓库分发,也不并入上述四类口径;引用时以本地文件为准。
- 交叉引用一律使用仓库内相对路径;指向模板仓库时给出 `specs/` 下的具体文件,不指向仓库首页。
- 本索引只登记与指向,不复制正文,也不记时间与进度;表格单元格一律居中。
