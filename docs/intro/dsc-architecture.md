# dsc 架构:三层组件

`dsc` 由三个逻辑层组件构成: `dsc-core`、`dsc-plugin-engine`、`dsc-market`。三者不是物理搬迁,而是按职责切开的逻辑层;每一层在仓库里各占一个目录,并各自维护一份说明。本文讲清三层各自负责什么、彼此靠什么接口交互、对插件暴露什么、信任边界落在哪里,以及这三层与 dsh 的对应关系。

## 分层总览

| 层 | 目录 | 一句话职责 | 依赖方向 |
|:---:|:---:|:---:|:---:|
| `dsc-core` | `src/components/dsc-core/` | 内核能力的归属与唯一出口 | 不依赖任何上层 |
| `dsc-plugin-engine` | `src/components/dsc-plugin-engine/` | 插件契约、生命周期与能力封装 | 只依赖 core |
| `dsc-market` | `src/components/dsc-market/` | 插件来源、目录与安装计划 | 依赖 engine 的类型与 core 的常量 |

依赖方向是单向的:上层可以引用下层的类型与常量,下层不得引用上层。唯一的例外是引擎的内置插件清单,详见「职责边界」。

三层都运行在浏览器里,没有任何后端进程:core 直接操作页面内的 store 与 IndexedDB,engine 用浏览器 `import()` 加载插件产物,market 用 core 提供的外源请求能力拉取静态文件。

## 职责边界

### 各层负责什么、不负责什么

| 层 | 负责 | 不负责 |
|:---:|:---:|:---:|
| `dsc-core` | 把会话、事件、提示、语言、外源请求、插件数据收敛成能力标识;凭证与票据校验;外源请求的协议、体积与超时约束;插件数据的配额与序列化校验;绕过检测与告警 | 不认识插件概念(无清单、无生命周期);不加载代码;不做限流与超时兜底;不判断来源与签名的可信性;不渲染任何插件界面 |
| `dsc-plugin-engine` | 清单校验与注册;安装、激活、停用、卸载与启动恢复;运行时加载与超时;能力白名单、限流与超时封装;贡献点分发;安装记录持久化;签名材料收集与验签;本地离线包预检与提交;内置插件装载 | 不定义来源与目录协议;不判断合集是否可信;不渲染界面;不直接读写聊天历史库;不引入 Node 能力 |
| `dsc-market` | 来源配置(两个内置来源与自定义来源);目录拉取(来源元信息、插件目录、版本清单、版本元信息);来源信任判定;安装计划生成;下载计数上报 | 不执行安装;不激活插件;不写安装记录;不渲染界面;不签名;不托管产物 |

关于 core 的归属: `src/app/`、`src/components/base/`、`src/components/chatInput/` 等业务界面、`src/services/` 下的会话、设置、附件、API 客户端、`src/i18n/`、`src/utils/` 在逻辑上属于 `dsc-core`,但代码位置保持不变。物理搬迁会破坏既有的相对导入、样式引用与构建入口,因此 core 只做能力收敛,不做目录搬迁。

### 边界核查结论

| 核查项 | 结论 | 依据 |
|:---:|:---:|:---:|
| market 是否直接执行安装 | 否,边界成立 | 市场只产出安装计划;安装由界面调用引擎的运行时安装接口完成,安装记录由引擎写入;计数上报与安装结果解耦,失败静默 |
| engine 是否承担信任判定 | 部分,方向正确但有交叉 | 合集可信性由市场按信任清单判定;引擎只做产物字节验签,给出通过、失败、未校验三种结论。两套结论各有独立词汇,不互相覆盖 |
| core 是否反向依赖上层 | 否,零依赖 | `src/components/dsc-core/` 内没有任何对 engine 或 market 的导入;core 只依赖 i18n、基础 Toast、services 与 utils,这些都在 core 自己的归属范围内 |
| `engine/builtin.ts` 是否直接 import `dsc-market` | 是,唯一一处反向导入 | 该文件在模块顶层导入市场插件的清单与插件对象,形成中间层到上层的运行时依赖 |

### 混用点、影响与建议

| 混用点 | 具体表现 | 影响 | 建议 |
|:---:|:---:|:---:|:---:|
| 引擎内置清单硬编码市场 | `engine/builtin.ts` 直接导入 `dsc-market` 的清单与插件对象 | 引擎无法在不引入市场的构建中存在;替换或移除内置市场必须改引擎源码;单测引擎会连带拉入市场的网络与信任依赖 | 由引擎提供内置插件登记入口,把内置清单外移到宿主装配层,让引擎只认识「内置插件集合」而不认识具体插件 |
| 清单生成出现两个权威 | 市场按版本元信息推导清单(含 id 归一化),产物也可自带清单;两处各自实现同一套 id 规则 | 同一插件经不同安装路径可能得到不同 id,进而出现重复安装或依赖匹配失败 | 把 id 归一化与清单推导收敛到一处,市场只搬运字段,规范化由引擎提供 |
| 来源信任结论只透传吊销 | 市场判定出证书缺失、证书链不通过、证书被吊销三种原因,只有吊销一项随安装请求传给引擎 | 安装记录里的可信标记只覆盖一种情形,界面需要同时读签名状态与可信标记才能判断风险 | 把来源可信结论整体作为独立字段随安装计划透传,引擎只存不改 |
| 内置插件绕过能力白名单直读宿主模块 | 市场直接导入 core 归属的信任清单模块与能力常量,不经过引擎的能力封装 | 信任清单读取不受限流与能力校验约束;第三方插件若也需要同类数据,没有可申请的能力 | 若信任判定长期留在市场,可考虑把信任清单作为安装计划或上下文的一部分显式提供,避免插件直接导入宿主服务 |
| 引擎告警绕过 core 的提示能力 | 引擎直接导入宿主 Toast 模块提示,core 的提示能力只服务插件 | 「core 是内核唯一出口」在告警这一项上不成立;方向仍是宿主界面,不构成对上层依赖 | 保持现状时应在文档中固定口径;若要严格收敛,可把引擎告警也走 core 的提示能力 |

以上五项均不影响当前功能,属于分层口径上的欠账。按边界划分,market 应只产出计划、engine 只按结论安装、core 不反向依赖,这三点当前成立;真正需要收敛的是「内置清单耦合」与「信任结论透传」。

## 接口交互

### core 对 engine 暴露什么

core 对 engine 只暴露两样东西: 一份能力表,和一对凭据。

| 交付物 | 内容 | 说明 |
|:---:|:---:|:---:|
| 凭证 | 由 core 签发、只在 core 内部可验证的符号令牌,持有人说自己是引擎 | 引擎启动时申请一次,全程复用;插件拿不到,也无法伪造 |
| 票据 | 一次调用一张,绑定单一能力标识,有效期 5 秒,消费即作废 | 引擎每次转发调用前签发,证明这一次调用属于已授予的能力 |
| 能力表 | 十个能力标识到实现的映射,覆盖会话列表、会话读取、会话改名、会话事件、宿主提示、当前语言、外源文本读取、计数请求、插件数据读写、插件数据清除 | 前八个在核心能力表内,其中外源文本读取只对内置插件生效;后两个只给引擎管理使用 |

调用约定: 引擎持有能力表后,每次调用都带上凭证与票据;core 先验凭证,再消费票据,能力标识不匹配、票据缺失或过期都按绕过处理,记录事件并抛错。凭证证明「调用方是引擎」,票据证明「这一次调用被允许」,两者缺一不可。绕过事件保留最近 50 条,告警按 3 秒合并成一次提示,由引擎注册的告警出口送达界面。

### engine 对插件暴露什么

引擎为每个插件构造一个上下文对象,里面是按能力白名单裁剪过的能力对象,而不是内核接口。

| 上下文成员 | 背后能力 | 形态 |
|:---:|:---:|:---:|
| 会话 | 会话列表、会话读取、会话改名 | 只读视图与改名,不含分支结构与请求快照 |
| 事件 | 会话事件 | 订阅贡献点,返回释放函数,由引擎在停用与卸载时执行 |
| 提示 | 宿主提示 | 用宿主既有文案键,不硬编码自然语言 |
| 设置 | 当前语言 | 只读 |
| 网络 | 外源文本读取,计数请求 | 只读文本与丢弃响应的计数请求,仅内置插件可用 |
| 数据 | 插件数据读写 | 键值读写,单插件 64KB |
| 日志 | 无 | 内存日志,上限 100 条,经引擎读取 |

每次成员调用依次经过白名单判定、限流、超时与票据签发: 清单没申请的能力直接拒绝;超出时间窗上限抛限流错误;超时与取消各有独立错误类型;网络类失败不弹宿主提示,由插件自行降级。上下文里没有 DOM、没有 store 句柄、没有 IndexedDB、没有附件原件、没有 API Key。

### market 如何取来源数据

市场是内置插件,拿到的上下文与第三方插件相同,取数全部走能力对象:

| 数据 | 获取方式 | 约束 |
|:---:|:---:|:---:|
| 来源元信息 | 来源根目录的元信息文件,含下载计数开关与计数地址 | 单请求 1 秒超时,按地址列表顺序回退 |
| 插件目录 | 来源根目录的目录文件,每条含插件名、作者、标签 | 并发上限 4,结构不符的条目跳过并计数 |
| 版本清单 | 每个插件的版本文件,给出最新版本与版本列表 | 最新版本必须是三段数字 |
| 展示信息 | 最新版本目录下的元信息文件 | 名称与版本必填,能力声明不合规则退回产物自带清单 |
| 来源配置 | 插件数据里的来源键 | 结构不符时退回内置默认来源 |
| 信任结论 | core 归属的信任清单模块 | 按来源 id 与名称命中合集,证书链结论直接取用 |

信任清单在插件激活时静默拉取一次: 两个镜像地址按顺序尝试,拉到的根证书必须与构建时内嵌的根证书逐字一致,否则整份清单不采信,所有来源按未校验处理。目录缓存只在内存里,5 分钟有效,不写入插件数据,避免挤占 64KB 配额。

### 安装请求如何从界面流向 engine

安装的发起方是界面,不是市场。市场只负责把「装什么、从哪里装、用什么材料验」整理成一份计划。

```
界面(插件面板的市场标签页)
  ├── 市场客户端.plan(来源 id, 目录条目)          # 只读快照 + 地址拼接,不发起安装
  │     └── 安装计划 { 产物地址, 清单, 来源类型, 证书或证书地址, 合集签名地址, 作者公钥地址, 作者签名地址 }
  └── 引擎.installFromUrl(产物地址, 清单, 来源材料)
        ├── 收集签名材料                            # 证书、公钥、两份签名,缺哪项就跳过对应校验
        ├── 验签产物字节                            # 通过 / 失败 / 未校验
        ├── 运行时导入产物                          # 浏览器 import,跨源时依赖托管方返回跨源头
        ├── 解析实例与产物自带清单                  # 实例、工厂、默认导出三种形态
        ├── 安装前校验                              # 清单字段、重名、版本兼容、冲突、依赖
        ├── 注册并激活                              # 构造上下文,调用插件激活入口,超时 5 秒
        └── 落盘                                    # 写安装记录,失败只记引擎日志
界面在安装成功后调市场客户端上报一次下载计数      # 与安装结果解耦,失败静默
```

几条固定的口径:

- 二次确认在界面层完成。来源不可信或未校验时,安装按钮第一次点击转为 3 秒确认态,确认后才调用引擎。
- 本地离线包同样是预检与提交两段: 预检只读文件并校验,返回待安装信息与提交函数,提交前不改动注册表与安装记录。
- 从地址直装是另一条入口,只给产物地址,清单由产物自带;这条路径没有来源材料,因此不做签名校验,来源类型记为其他在线来源。
- 安装成功后引擎自动激活;宿主直接注册插件对象的接口只登记不激活。

## 对外暴露面

三块内容必须分开看: 插件依赖的公开契约、可以随时改的内部实现、只有宿主能用的专用能力。

### 插件可见的公开契约

| 契约 | 内容 |
|:---:|:---:|
| 清单字段 | 标识、名称、版本、兼容的核心版本范围、依赖、冲突、能力、贡献点 |
| 插件对象 | 激活入口(可返回 Promise,超时 5 秒)与可选的停用入口(超时 3 秒) |
| 产物导出 | 具名激活入口、默认导出、插件工厂三种形态之一,可附带具名清单;模块顶层清单优先 |
| 上下文成员 | 会话、事件、提示、设置、网络、数据、日志,共七项 |
| 能力范围 | 第三方插件可申请七项;外源文本读取只对内置插件开放,第三方声明时按未知能力拒绝 |
| 贡献点 | 只有会话变更一个 |
| 限流与超时 | 每项能力有独立的时间窗上限与单次超时,具体数值见插件开发规范 |
| 错误类型 | 能力未授予、限流、超时、取消四种,另有插件数据错误与外源请求错误 |
| 安装拒绝原因 | 清单非法、未知能力、未知贡献点、版本不兼容、重名、缺依赖、冲突、加载失败、产物非法、签名无效,以及离线包专有的扩展名、解包、缺元信息、缺产物、元信息非法、体积超限 |

这份契约一旦改动就影响第三方插件,任何字段增删都要按规范流程走。公开契约的完整条文见 [dsc 插件开发规范](../user/develop/basic/plugin-develop-spec.md) 与 [dsc 插件产物规范](../user/develop/basic/plugin-product-spec.md)。

### 内部实现

以下内容不构成对外承诺,可以在任意版本调整:

| 内部实现 | 说明 |
|:---:|:---:|
| 凭证与票据结构 | 符号令牌、票据编号、能力绑定与有效期,都只在 core 内部有效 |
| 能力表与注册方式 | 能力标识到实现的映射,以及首次打开时一次性注册的做法 |
| 能力代理与策略表 | 白名单、限流窗口、超时数值的实现位置 |
| 安装记录字段 | 存储里的字段名、签名材料的编码方式、启动恢复的并发上限 |
| 离线包解析 | 解包方式、目录取舍、元信息到清单的推导 |
| 验签实现 | 证书解析、CMS 分离验签、作者裸签名验签,以及证书链与 CMS 模块的按需加载 |
| 市场客户端状态 | 来源运行态、内存缓存、状态版本号与订阅方式 |
| 加载方式 | 运行时导入的写法、超时实现、本地代码重建模块的做法 |

### 宿主专用能力

这些能力只有宿主与引擎能用,插件清单申请不到,也不会出现在插件上下文里:

| 能力 | 谁在用 | 为什么不对插件开放 |
|:---:|:---:|:---:|
| 计数请求(能力标识 `net:fetch-post`,外源 JSON POST) | 市场,经上下文的网络成员间接使用 | 只服务于下载计数,响应体被丢弃;插件清单不能声明它,只能随外源读取的授予间接使用 |
| 插件数据清除 | 引擎在卸载时调用 | 会清除单个插件的全部数据,不能由插件自行触发 |
| 外源文本读取的内置限定 | 市场等内置插件 | 第三方插件申请时按未知能力拒绝,无法与不存在的能力区分 |
| 引擎管理接口 | 宿主界面 | 安装、运行时安装、离线包预检与提交、激活、停用、卸载、列表、日志、引擎日志、绕过事件 |
| 界面侧安装入口 | 插件面板 | 从地址直装与本地离线包导入,决定安装请求的发起时机 |

## 信任边界

信任在这三层里被切成两段: 合集是否可信由市场判定,产物字节是否与签名匹配由引擎判定。

| 环节 | 发生在哪一层 | 做法 |
|:---:|:---:|:---:|
| 来源可信判定 | `dsc-market` | 按来源 id 与名称在信任清单里找合集,拉取该合集的终端签名证书,用根证书校验证书链;可选启用吊销检查 |
| 证书链锚定 | `dsc-market` | 根证书在构建时内嵌,清单里的根证书必须逐字一致,否则整份清单不采信 |
| 产物字节验签 | `dsc-plugin-engine` | 合集分离签名与作者裸签名各自有材料才校验,全部通过为通过;验签只证明签名与该证书匹配,不校验证书链 |
| 来源可信结论的落盘 | `dsc-plugin-engine` | 只保存市场透传的吊销结论,其余原因体现为界面提示 |
| 界面提示与二次确认 | 插件面板 | 展示可信状态与失败原因,决定是否进入 3 秒确认态 |

能力白名单有三道关口,都在引擎,能力实现都在 core:

| 关口 | 时机 | 判定 |
|:---:|:---:|:---:|
| 清单申请 | 安装前 | 能力必须在核心能力表内且不重复;外源读取要求插件 id 属于内置集合,否则按未知能力拒绝 |
| 安装校验 | 注册前 | 同一份清单再校验一次,连同重名、版本兼容、冲突与依赖一起判定 |
| 调用时 | 每次成员调用 | 再校验清单是否授予该能力,并对外源读取补一次内置限定,防止绕过安装校验直接取用 |

失败一律只警告、不阻断:

| 情形 | 行为 |
|:---:|:---:|
| 安装时验签不通过 | 仍然安装并激活,安装记录标记为签名失败与不可信,界面提示用户自行判断 |
| 启动恢复时验签不通过 | 仍然加载并激活,记录标记为不可信,界面保留标识 |
| 合集证书被吊销 | 同样只提示,不阻断安装,记录标记为不可信 |
| 信任清单根证书不一致 | 整份清单不采信,所有来源按未校验处理,只提示一次 |
| 拉取产物字节失败 | 视为网络问题而不是篡改,按恢复失败处理,不标记不可信 |
| 来源不可信或未校验 | 目录照常列出,安装前需用户确认 |

需要留意的一处事实: 引擎的合集验签把签名者证书当作已通过链校验的输入,自身不做链锚定。因此只有经由市场生成的安装计划才带可信证书;从地址直装与本地离线包这两条路径,只能证明签名与随包材料匹配,不能证明签发方可信。展示用的版本元信息签名不在运行时校验范围内,展示信息按未验签处理。

## 两个容易混淆的区分

### dsc-market 与 omdsc-market

| 项 | `dsc-market` | `omdsc-market` |
|:---:|:---:|:---:|
| 是什么 | DeepSeek-Chat-Enhanced 内置的插件市场壳子,本身就是一个内置插件 | awesome-dsc-plugin 合集的专职前端展示机,源码为独立仓库 |
| 位置 | 仓库内 `src/components/dsc-market/`,由引擎的内置清单装载 | 仓库外,读者通过产品文档中的链接访问 |
| 负责 | 来源管理、目录拉取、来源信任判定、安装计划生成、下载计数上报 | 页面展示: 插件列表、插件详情、跳转入口 |
| 不负责 | 不渲染界面、不执行安装、不托管产物、不签名 | 不参与插件收录、不生成安装计划、不写安装记录、不决定插件可用性 |
| 与本体关系 | 插件面板的市场标签页通过它的查询接口取数,安装请求由界面转交引擎 | 独立产品,与本体没有运行时代码关系 |

两者的职责分离是刻意的: 收录与判定留在本体内的市场壳子里,展示交给独立的展示站点。展示站点上看到什么,由合集发布什么决定;本体安装什么,由市场壳子的来源配置与信任判定决定。

### dsc-inner-plugin 与 awesome-dsc-plugin

| 项 | `dsc-inner-plugin` | `awesome-dsc-plugin` |
|:---:|:---:|:---:|
| 性质 | dsc 背书、由 dsc 直接签名发布的内部插件索引 | 社区合集 |
| 签发方 | dsc 自身,信任锚与本体同源,因此本身可信 | 持有终端签名证书的合集方,凭根证书签发的证书建立信任 |
| 收录内容 | 从 DeepSeek-Chat-Enhanced 本体解耦出来的可选内部插件 | 社区提交的第三方插件 |
| 分发地址 | 单一静态地址 | 分发加速、原始地址、静态页面三级回退 |
| 默认优先级 | 首位 | 次位 |
| 安装流程 | 与社区合集完全一致 | 与内部索引完全一致 |

信任判定的代码不区分这两者: 两者都按来源 id 命中信任清单,走同一条验签与安装流程,差别只在签发方、收录口径、分发地址与默认优先级。来源类型分别记为内部与精选,用于安装记录的来源标注。

## 与 dsh 的对应关系

dsc 的插件机制是浏览器内的最小实现,概念上与 dsh 一一对应,但落地手段完全不同。

| dsh 概念 | dsc 对应 | 差异要点 |
|:---:|:---:|:---:|
| 插件声明与清单 | 清单对象,安装时校验 | dsc 内联声明,不读包描述文件 |
| 注册与加载 | 宿主注册对象,或运行时导入产物 | dsc 只有浏览器 `import()`,没有进程内模块系统 |
| 生命周期 | 已注册、已激活、已停用、失败 | dsc 用四个状态加释放函数,没有协程式副作用管理 |
| 服务与依赖注入 | 上下文能力对象与依赖校验 | dsc 只给白名单能力,不给服务容器 |
| 权限与沙箱 | 能力白名单、凭证与票据、限流与超时、内置白名单 | dsc 没有进程隔离,靠接口裁剪与调用约束 |
| 内置插件 | 内置清单,启动时先于外部插件装载 | dsc 的内置清单目前硬编码市场一项 |
| 配置持久化 | 安装记录写 IndexedDB,插件数据写本地存储 | dsc 分两处存放,配额与生命周期不同 |
| 热重载 | 未实现,刷新页面重新加载 | 纯前端形态下的取舍 |

完整的理念、服务边界与技术架构对比见 [DSC 与 DSH 的设计异同](dsc-diff-dsh.md)。
