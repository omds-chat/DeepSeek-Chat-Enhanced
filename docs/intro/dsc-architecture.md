# dsc 架构:三层组件

`dsc` 由三个逻辑层组件构成: `dsc-core`、`dsc-plugin-engine`、`dsc-market`。三者不是物理搬迁,而是按职责切开的逻辑层;每一层在仓库里各占一个目录,并各自维护一份说明。三个组件同属 `dsc` 一个产品,分层只是内部逻辑上的分层,不是可以独立部署的模块,因此在外部看来它们不能单独工作,组件之间互相 import 是正常实现方式,不构成职责边界问题。本文讲清三层各自负责什么、彼此靠什么接口交互、对插件暴露什么、信任边界落在哪里,以及这三层与 dsh 的对应关系。

## 分层总览

| 层 | 目录 | 一句话职责 | 依赖方向 |
|:---:|:---:|:---:|:---:|
| `dsc-core` | `src/components/dsc-core/` | 内核能力的归属与唯一出口 | 不依赖任何上层 |
| `dsc-plugin-engine` | `src/components/dsc-plugin-engine/` | 插件契约、生命周期与能力封装 | 只依赖 core |
| `dsc-market` | `src/components/dsc-market/` | 插件来源、目录与安装计划 | 依赖 engine 的类型与 core 的常量 |

依赖方向描述的是逻辑层次,不是编译期隔离:上层引用下层的类型与常量是常规做法;下层引用上层的代码同样可以出现,例如引擎持有内置插件清单,其中包含内置市场。这类引用属于同一产品内的正常装配,详见「职责边界」。

三层都运行在浏览器里,没有任何后端进程:core 直接操作页面内的 store 与 IndexedDB,engine 用 `fetch` 取产物字节后以 Blob 地址 `import` 加载插件产物,market 用 core 提供的外源请求能力拉取静态文件。

## 职责边界

### 各层负责什么、不负责什么

| 层 | 负责 | 不负责 |
|:---:|:---:|:---:|
| `dsc-core` | 把会话、事件、提示、语言、外源请求、资产读取、插件数据收敛成能力标识;凭证与票据校验;外源请求与资产读取的协议、体积与超时约束;插件数据的配额与序列化校验;绕过检测与告警 | 不认识插件概念(无清单、无生命周期);不加载代码;不做限流与超时兜底;不判断来源与签名的可信性;不渲染任何插件界面 |
| `dsc-plugin-engine` | 清单校验与注册;安装、激活、停用、卸载与启动恢复;运行时加载与超时;能力白名单、限流与超时封装;挂载点分发;安装记录持久化;签名材料收集与验签;本地离线包预检与提交;内置插件装载 | 不定义来源与目录协议;不判断合集是否可信;不渲染界面;不直接读写聊天历史库;不引入 Node 能力 |
| `dsc-market` | 来源配置(内置来源与自定义来源);目录拉取(来源元信息、插件目录索引、版本清单、版本元信息);来源信任判定;安装计划生成;下载计数上报 | 不执行安装;不激活插件;不写安装记录;不渲染界面;不签名;不托管产物 |

挂载点是插件声明要挂到宿主哪个回调位置:清单用 `mounts` 列出位置,引擎据此把宿主回调分发给登记过处理器的插件。

关于 core 的归属: `src/app/`、`src/components/base/`、`src/components/chatInput/` 等业务界面、`src/services/` 下的会话、设置、附件、API 客户端、`src/i18n/`、`src/utils/` 在逻辑上属于 `dsc-core`,但代码位置保持不变。物理搬迁会破坏既有的相对导入、样式引用与构建入口,因此 core 只做能力收敛,不做目录搬迁。

### 边界核查结论

| 核查项 | 结论 | 依据 |
|:---:|:---:|:---:|
| market 是否直接执行安装 | 否,边界成立 | 市场只产出安装计划;安装由界面调用引擎的运行时安装接口完成,安装记录由引擎写入;计数上报与安装结果解耦,失败静默 |
| engine 是否承担信任判定 | 是,两段结论分工明确 | 证书链与来源结论由引擎判定;市场只给出信任清单的展示结论。两套结论各有独立词汇,不互相覆盖 |
| core 是否反向依赖上层 | 否,零依赖 | `src/components/dsc-core/` 内没有任何对 engine 或 market 的导入;core 只依赖 i18n、基础 Toast、services 与 utils,这些都在 core 自己的归属范围内 |
| `engine/builtin.ts` 是否直接 import `dsc-market` | 是,属于同一产品的正常装配 | 该文件在模块顶层导入内置市场的清单与插件对象;内置市场是引擎内置插件集合中的一项,两者同属 dsc,分层不要求编译期隔离 |

### 内部分层约定

三个组件同属一个产品,组件之间互相 import 是正常实现方式;以下两条与「谁引用谁」无关,是真正影响内部一致性的约定。

| 约定 | 现状 | 风险 | 建议 |
|:---:|:---:|:---:|:---:|
| 插件 id 规则只有一处权威 | 已收敛到 `dsc-plugin-engine/pluginId.ts`;离线包、在线安装与插件市场都引用这一份实现,市场侧只保留同名再导出 | 无 | 保持单处实现,新增安装路径只引用该模块,不复制规则 |
| 安装记录承载完整可信结论 | 市场判定出证书缺失、证书链不通过、证书被吊销三种原因,安装计划把 `trustFailure` 原样透传,`dsc-plugin-engine/index.ts` 写入 `trust_failure`;`trusted` 布尔字段只对吊销置否 | 判定要同时读 `source_trust`、`trust_failure` 与签名结论,`trusted` 与这三者的口径不一致 | 新增判定只写 `source_trust` 与 `trust_failure`,`trusted` 仅作旧记录兼容,不再扩展含义 |

除此之外,market 只产出安装计划、engine 只按结论安装、core 不反向依赖上层,这三点在当前实现中成立。

### 同一产品内的正常引用

以下三处属于同一产品内部的分层实现方式,记录在此以免误读。

- 内置插件清单由引擎持有: `engine/builtin.ts` 在模块顶层导入内置市场的清单与插件对象。内置市场是引擎内置插件集合中的一项,清单由引擎持有,属于同一产品的正常装配;集合里有哪几项由产品装配决定,引擎只按集合装载。
- 内置插件直接使用宿主模块: 市场等内置插件导入 core 归属的信任清单模块与能力常量。内置插件与宿主同属 dsc,直接使用宿主模块是设计内行为;能力白名单约束的对象是第三方插件,第三方插件既拿不到这些模块,也没有对应能力可申请。
- 引擎告警经宿主提示呈现: 引擎直接导入宿主 Toast 模块提示。告警最终仍由宿主界面呈现,属于同一产品的展示层,不构成对上层依赖;core 的提示能力只服务插件。

## 接口交互

### core 对 engine 暴露什么

core 对 engine 只暴露两样东西: 一份能力表,和一对凭据。

| 交付物 | 内容 | 说明 |
|:---:|:---:|:---:|
| 凭证 | 由 core 签发、只在 core 内部可验证的符号令牌,持有人说自己是引擎 | 引擎启动时申请一次,全程复用;插件拿不到,也无法伪造 |
| 票据 | 一次调用一张,绑定单一能力标识,有效期 5 秒,消费即作废 | 引擎每次转发调用前签发,证明这一次调用属于已授予的能力 |
| 能力表 | 内核能力标识到实现的映射,按业务域覆盖会话读写、会话事件、宿主提示、设置、网络、资产、插件数据、请求前补丁与供应端点执行等域 | 能力按业务域打包、写能力按最小可回滚单位收敛,粒度并不齐整;哪些标识对插件可见、哪些只给引擎管理使用,能力清单以 [职责契约](../design/core-engine-contract.md) 为准。请求补丁的 `chat:request`、来源声明的 `provider:source` 与按端点执行的 `provider:run` 没有 core 侧实现,登记与调用都在引擎内完成,不进这张表 |

调用约定: 引擎持有能力表后,每次调用都带上凭证与票据;core 先验凭证,再消费票据,能力标识不匹配、票据缺失或过期都按绕过处理,记录事件并抛错。凭证证明「调用方是引擎」,票据证明「这一次调用被允许」,两者缺一不可。绕过事件保留最近 50 条,告警按 3 秒合并成一次提示,由引擎注册的告警出口送达界面。

### engine 对插件暴露什么

引擎为每个插件构造一个上下文对象,里面是按能力白名单裁剪过的能力对象,而不是内核接口。

| 上下文成员 | 背后能力 | 形态 |
|:---:|:---:|:---:|
| 会话 | 会话列表、会话读取、会话改名 | 只读视图与改名,不含分支结构与请求快照 |
| 事件 | 会话事件 | 订阅挂载点,返回释放函数,由引擎在停用与卸载时执行 |
| 提示 | 宿主提示 | 用宿主既有文案键,不硬编码自然语言 |
| 设置 | 当前语言 | 只读 |
| 网络 | 外源文本读取,计数请求 | 只读文本与丢弃响应的计数请求,仅内置插件可用 |
| 资产 | 资产读取 | 按地址读取远端文本或字节,三态结果原样返回,仅 https 与回环地址 |
| 数据 | 插件数据读写 | 键值读写,单插件 64KB |
| 请求前补丁 | 请求补丁 | 登记处理器,每次请求前调用一次,字段由引擎收敛 |
| 供应端点 | 供应端点声明与执行 | 声明端点描述;按选中的端点执行一次调用,凭证与请求组装都不在插件侧 |
| 日志 | 无 | 内存日志,上限 100 条,经引擎读取 |

每次成员调用依次经过白名单判定、限流、超时与票据签发: 清单没申请的能力直接拒绝;超出时间窗上限抛限流错误;超时与取消各有独立错误类型;网络类失败不弹宿主提示,由插件自行降级。资产读取只在该插件首次访问某个来源时提示一次,之后的失败只写插件日志。登记型成员(`events.on`、`chat.onBeforeRequest`)的限流按登记次数计,事件回调与请求前调用由引擎发起,不再占用名额。上下文里没有 DOM、没有 store 句柄、没有 IndexedDB、没有附件原件、没有 API Key。

### market 如何取来源数据

市场是内置插件,拿到的上下文与第三方插件相同,取数全部走能力对象:

| 数据 | 获取方式 | 约束 |
|:---:|:---:|:---:|
| 来源元信息 | 来源根目录的元信息文件,含下载计数开关与计数地址 | 单请求 1 秒超时,按地址列表顺序回退 |
| 插件目录索引 | 来源根目录的 `plugins.json`,每条含插件名、作者、标签 | 并发上限 4,结构不符的条目跳过并计数 |
| 版本清单 | 每个插件的版本文件,给出最新版本与版本列表 | 最新版本必须是三段数字 |
| 展示信息 | 最新版本目录下的元信息文件 | 名称与版本必填,能力声明不合规则退回产物自带清单 |
| 来源配置 | 插件数据里的来源键 | 结构不符时退回内置默认来源 |
| 信任清单判定 | core 归属的信任清单模块 | 按来源 id 与名称命中合集,只给出是否被官方认可的展示结论 |

信任清单在插件激活时静默拉取一次: 两个镜像地址按顺序尝试,拉到的根证书与构建时内嵌的根证书比对,不一致时以构建内置的为准并留一条控制台提示;清单登记的合集证书仍用内置根证书校验证书链。目录缓存只在内存里,5 分钟有效,不写入插件数据,避免挤占 64KB 配额。

### 安装请求如何从界面流向 engine

安装的发起方是界面,不是市场。市场只负责把「装什么、从哪里装、用什么材料验」整理成一份计划。

```
界面(插件面板的市场标签页)
  ├── 市场客户端.plan(来源 id, 目录条目)          # 只读快照 + 地址拼接,不发起安装
  │     └── 安装计划 { 产物地址, 清单, 来源类型, 证书或证书地址, 合集签名地址, 作者公钥地址, 作者签名地址 }
  └── 引擎.installFromUrl(产物地址, 清单, 来源材料)
        ├── 收集签名材料                            # 证书、公钥、两份签名,缺哪项就跳过对应校验
        ├── 验签产物字节                            # 通过 / 失败 / 未校验
        ├── 运行时导入产物                          # 按 Blob 地址 import,取件跨源时依赖托管方返回跨源头
        ├── 解析实例与产物自带清单                  # 实例、工厂、默认导出三种形态
        ├── 安装前校验                              # 清单字段、重名、版本兼容、冲突(只检出与警告,不拒绝)、依赖
        ├── 注册并激活                              # 构造上下文,调用插件激活入口,超时 5 秒
        └── 落盘                                    # 写安装记录,失败只记引擎日志
界面在安装成功后调市场客户端上报一次下载计数      # 与安装结果解耦,失败静默
```

几条固定的口径:

- 二次确认在界面层完成。来源不可信或未校验时,安装按钮第一次点击转为 3 秒确认态,确认后才调用引擎。
- 本地离线包同样是预检与提交两段: 预检只读文件并校验,返回待安装信息与提交函数,提交前不改动注册表与安装记录。
- 从地址直装是另一条入口,只给产物地址,清单由产物自带;这条路径没有来源材料,因此不做签名校验,来源类型记为其他在线来源。
- 安装成功后引擎自动激活;宿主直接注册插件对象的接口只登记不激活。

## 对外暴露面

三块内容必须分开看: 插件依赖的公开契约、可以随时改的内部实现、只有宿主能用的专用能力。

### 插件可见的公开契约

| 契约 | 内容 |
|:---:|:---:|
| 清单字段 | 标识、名称、版本、兼容的核心版本范围、依赖、冲突、能力、挂载点 |
| 插件对象 | 激活入口(可返回 Promise,超时 5 秒)与可选的停用入口(超时 3 秒) |
| 产物导出 | 具名激活入口、默认导出、插件工厂三种形态之一,可附带具名清单;模块顶层清单优先 |
| 上下文成员 | 会话、事件、提示、设置、网络、资产、数据、请求前补丁、供应端点、日志,共十项 |
| 能力范围 | 读能力按业务域打包、写能力按粒度收敛,不在此复述数量;第三方插件可申请的范围、内置限定(外源文本读取、计数请求)与供应端点两项(`provider:source`、`provider:run`)的归属,能力清单以 [职责契约](../design/core-engine-contract.md) 为准 |
| 挂载点 | 插件声明挂载位置,登记处理器前须把位置写入清单 `mounts`;开放哪些挂载点,能力清单以 [职责契约](../design/core-engine-contract.md) 为准 |
| 限流与超时 | 每项能力有独立的时间窗上限;异步成员另有单次超时,同步成员没有超时;具体数值见插件开发规范与引擎说明 |
| 错误类型 | 能力未授予、限流、超时、取消四种,另有插件数据错误、外源请求错误与资产读取错误;资产读取的“拿到状态码”与“没有状态码”不是错误,按返回值交给插件 |
| 安装拒绝原因 | 清单非法、未知能力、未知挂载点、版本不兼容、重名、缺依赖、加载失败、产物非法、签名无效,以及离线包专有的扩展名、解包、缺元信息、缺产物、元信息非法、体积超限;冲突不属于拒绝原因,安装总是成功并按对方启用状态发警告与停用新插件 |

这份契约一旦改动就影响第三方插件,任何字段增删都要按规范流程走。公开契约的完整条文见模板仓库的 [dsc 插件开发规范](https://github.com/omds-chat/dsc-plugin-template/blob/main/specs/plugin-develop-spec.md) 与 [dsc 插件运行时规范](https://github.com/omds-chat/dsc-plugin-template/blob/main/specs/plugin-runtime-spec.md);本仓库的 [dsc 插件产物规范](../user/develop/basic/plugin-product-spec.md) 只保留模板未覆盖的签名与持久化内容。

### 内部实现

以下内容不构成对外承诺,可以在任意版本调整:

| 内部实现 | 说明 |
|:---:|:---:|
| 凭证与票据结构 | 符号令牌、票据编号、能力绑定与有效期,都只在 core 内部有效 |
| 能力表与注册方式 | 能力标识到实现的映射,以及首次打开时一次性注册的做法 |
| 能力代理与策略表 | 白名单、限流窗口、超时数值的实现位置 |
| 安装记录字段 | 存储里的字段名、签名材料的编码方式、启动恢复的并发上限 |
| 离线包解析 | 解包方式、目录取舍、元信息到清单的推导 |
| 验签实现 | 证书解析、CMS 分离验签、作者裸签名验签,以及证书链与 CMS 模块的按需加载 |
| 市场客户端状态 | 来源运行态、内存缓存、状态版本号与订阅方式 |
| 加载方式 | 运行时导入的写法、超时实现、本地代码重建模块的做法 |

### 宿主专用能力

这些能力只有宿主与引擎能用,插件清单申请不到,也不会出现在插件上下文里:

| 能力 | 谁在用 | 为什么不对插件开放 |
|:---:|:---:|:---:|
| 计数请求(能力标识 `net:fetch-post`,外源 JSON POST) | 市场,经上下文的网络成员间接使用 | 只服务于下载计数,响应体被丢弃;插件清单不能声明它,只能随外源读取的授予间接使用 |
| 插件数据清除 | 宿主设置的数据管理调用 | 会清除单个插件的全部数据,不能由插件自行触发 |
| 外源文本读取的内置限定 | 市场等内置插件 | 第三方插件申请时按未知能力拒绝,无法与不存在的能力区分 |
| 引擎管理接口 | 宿主界面 | 安装、运行时安装、离线包预检与提交、激活、停用、卸载、列表、日志、引擎日志、绕过事件 |
| 界面侧安装入口 | 插件面板 | 从地址直装与本地离线包导入,决定安装请求的发起时机 |

## 信任边界

信任在这三层里被切成两段: 证书链与来源结论由引擎判定,信任清单只给出「是否被官方认可」的展示结论。

| 环节 | 发生在哪一层 | 做法 |
|:---:|:---:|:---:|
| 来源清单判定 | `dsc-market` | 按来源 id 与名称在信任清单里找合集,给出是否被官方认可的展示结论,不再决定来源结论 |
| 证书链锚定 | `dsc-plugin-engine` | 根证书在构建时内嵌,清单证书与来源证书(按 `certs/<合集 id>/<合集 id>-eec.crt`、旧站点扁平的 `certs/<合集 id>-eec.crt`、最旧的 `eec.pem` 三档依次取)都先过链校验;清单根证书只用于比对,不一致时以内置为准 |
| 产物字节验签 | `dsc-plugin-engine` | 链校验通过后才做合集分离签名验签,链不通过时不做 CMS 验签;作者裸签名各自有材料才校验 |
| 来源结论的落盘 | `dsc-plugin-engine` | 按本地链校验与验签结论写入,`eec_anchored` 记录链是否通过;信任清单判定另存供界面展示 |
| 界面提示与二次确认 | 插件面板 | 展示可信状态与失败原因,决定是否进入 3 秒确认态 |

能力白名单有三道关口,都在引擎,能力实现都在 core:

| 关口 | 时机 | 判定 |
|:---:|:---:|:---:|
| 清单申请 | 安装前 | 能力必须在核心能力表内且不重复;外源读取要求插件 id 属于内置集合,否则按未知能力拒绝;资产读取不要求内置集合 |
| 安装校验 | 注册前 | 同一份清单再校验一次,连同重名、版本兼容、冲突与依赖一起判定;冲突只检出与警告,不拒绝安装 |
| 调用时 | 每次成员调用 | 再校验清单是否授予该能力,并对外源读取补一次内置限定,防止绕过安装校验直接取用 |

失败一律只警告、不阻断:

| 情形 | 行为 |
|:---:|:---:|
| 安装时验签不通过 | 仍然安装并激活,安装记录标记为签名失败与不可信,界面提示用户自行判断 |
| 启动恢复时验签不通过 | 仍然加载并激活,记录标记为不可信,界面保留标识 |
| 合集证书被吊销 | 同样只提示,不阻断安装,记录标记为不可信 |
| 信任清单根证书不一致 | 仍按内置根证书校验,清单判定标记为不一致并提示一次 |
| 拉取产物字节失败 | 视为网络问题而不是篡改,按恢复失败处理,不标记不可信 |
| 来源不可信或未登记 | 目录照常列出,安装前需用户确认 |

需要留意的一处事实: 引擎的合集验签会先用内置根证书校验证书链,链通过后才做 CMS 验签,未校验链的证书不会进入验签。从地址直装时只要调用方给出 `eec` 或 `eecUrls`,来源结论就按本地校验结论给出;没有证书时结论为 `failed`(原因 `other`),不会把未校验的证书当作可信输入。本地离线包只带作者签名,不参与合集链判定。展示用的版本元信息签名不在运行时校验范围内,展示信息按未验签处理。

## 两个容易混淆的区分

### dsc-market 与合集站点

| 项 | `dsc-market` | 合集站点 |
|:---:|:---:|:---:|
| 是什么 | DeepSeek-Chat-Enhanced 内置的插件市场壳子,负责来源管理与安装 | awesome-dsc-plugin 的 Pages 站点,负责收录、展示与插件托管 |
| 位置 | 仓库内 `src/components/dsc-market/`,由引擎的内置清单装载 | 仓库外,读者通过产品文档中的链接访问 |
| 负责 | 来源管理、目录拉取、来源信任判定、安装计划生成、下载计数上报 | 收录与展示: 插件列表、插件详情、跳转入口,并托管插件产物 |
| 不负责 | 不渲染界面、不执行安装、不托管产物、不签名 | 不生成安装计划、不写安装记录、不决定插件可用性 |
| 与本体关系 | 插件面板的市场标签页通过它的查询接口取数,安装请求由界面转交引擎 | 与本体没有运行时代码关系,只在来源配置与文档链接中与本体相接 |

两者的职责分离是刻意的: 来源管理与安装判定留在本体内的市场壳子里,收录、展示与插件托管交给合集站点。合集站点上看到什么,由合集收录什么决定;本体安装什么,由市场壳子的来源配置与信任判定决定。合集站点的职责不再由独立仓库承担,原独立的市场仓库已废除,其展示功能并入 awesome-dsc-plugin 的 Pages。

### dsc-inner-plugin 与 awesome-dsc-plugin

| 项 | `dsc-inner-plugin` | `awesome-dsc-plugin` |
|:---:|:---:|:---:|
| 性质 | dsc 背书、由 dsc 直接签名发布的内部插件索引 | 社区合集 |
| 签发方 | dsc 自身,信任锚与本体同源,因此本身可信 | 持有终端签名证书的合集方,凭根证书签发的证书建立信任 |
| 收录内容 | 从 DeepSeek-Chat-Enhanced 本体解耦出来的可选内部插件 | 社区提交的第三方插件 |
| 分发地址 | 单一静态地址 | 分发加速、原始地址、静态页面三级回退 |
| 默认优先级 | 首位 | 次位 |
| 安装流程 | 与社区合集完全一致 | 与内部索引完全一致 |

信任清单判定的代码不区分这两者: 两者都按来源 id 命中清单,走同一条验签与安装流程,差别只在签发方、收录口径、分发地址与默认优先级。来源类型分别记为内部与精选,用于安装记录的来源标注。

## 与 dsh 的对应关系

dsc 的插件机制是浏览器内的最小实现,概念上与 dsh 一一对应,但落地手段完全不同。

| dsh 概念 | dsc 对应 | 差异要点 |
|:---:|:---:|:---:|
| 插件声明与清单 | 清单对象,安装时校验 | dsc 内联声明,不读包描述文件 |
| 注册与加载 | 宿主注册对象,或运行时导入产物 | dsc 只有浏览器内的 ESM 加载,没有进程内模块系统 |
| 生命周期 | 已注册、已激活、已停用、失败 | dsc 用四个状态加释放函数,没有协程式副作用管理 |
| 服务与依赖注入 | 上下文能力对象与依赖校验 | dsc 只给白名单能力,不给服务容器 |
| 权限与沙箱 | 能力白名单、凭证与票据、限流与超时、内置白名单 | dsc 没有进程隔离,靠接口裁剪与调用约束 |
| 内置插件 | 内置清单,启动时先于外部插件装载 | dsc 的内置清单由引擎持有,市场是其中一项 |
| 配置持久化 | 安装记录写 IndexedDB,插件数据写本地存储 | dsc 分两处存放,配额与生命周期不同 |
| 热重载 | 未实现,刷新页面重新加载 | 纯前端形态下的取舍 |

完整的理念、服务边界与技术架构对比见 [DSC 与 DSH 的设计异同](dsc-diff-dsh.md)。
